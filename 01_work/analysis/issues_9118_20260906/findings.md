# 9118 사용자 보고 1차 조사

## 원인 추적 결과 (후속, 수정/빌드 없음)

재현: `python 02_scripts/audit_arc1_9118_runtime.py` 및 `python 02_scripts/audit_arc1_9118_causes.py`. RAM은 Bus+64를 EXE 여섯 48B 앵커로 검증, VRAM은 유일한 GPU-VRAM 마커로 위치 결정했다. 기존 파서 버전 가드를 우회하거나 세이브 헤더를 바꾸지 않았다. 분석 스크립트 최초 numpy 의존 실패는 표준 array/PIL로 제거했다.

### 3/4: 16px 글자에 원본 38px 설명창이 남아 있음

- 양쪽 실제 배경 x/y/w/h는 130/110/160/38. 설명 객체 0x801F031C의 glyph rows는 y116/y132, 높이16이다. 두 번째 줄 아래끝148이 창 아래끝148과 같아 하단 여백이 없고 테두리를 침범한다.
- EXE 0x8016C54C의 `ori a3,zero,0x26`(38px 배경), 0x8016C778의 `ori a2,zero,0x1C`(28px 텍스트 공간)는 원본과 동일. 12px 전제의 창/공간을 16px 출력에 맞추지 못한 원인이다. 단순 슬롯 부족과 별개다.
- 6번 스킬창은 다른 초기화 경로 0x80161A74에서 높이52를 전달하며 실제 x/y/w/h 80/103/160/52로 확인됐다. 3/4 창에도 이미 적용됐다고 볼 수 없다.

### 6: 서로 다른 안내 소비자 중 대사만 LR 복원

- V359 e7_semantic_text_repair의 LR_NEW는 4/S4033.DAT:0x48102의 프리 커서 설명이다. 전투 하단 안내는 PSX.EXE pointer0x82360 ->0x80F02로 별개다. build_ui_safe_v32부터 해당 안내를 LR 없는 `다음 대상을 선택합니다`로 입력했고 현재까지 남아 있다.
- 코드/글리프 공급 실패가 아니라 수정 대상 누락. 기존 L/R 코드는 사용 가능하다. 재배치/길이 변경은 이번 조사에서 하지 않았다.

### 8: 범위 커서 업로드 영역과 비텍스트 애니메이션 독자의 실제 충돌

- 사용자 확대 이미지의 보라색 사각 테두리/흰 점을 대상으로 조사했다. 1/8번의 활성 OT context0x801AE1E4, parity0, 725개 명령을 sentinel까지 추적(순환/조기중단 없음).
- 실제 활성 FT4 두 개 0x801DCE54/0x801DCE04(order553/555)는 같은 화면 좌표 x224..255/y87..118, CLUT0x7DCC를 사용한다.
- 정상 1번은 tpage0x0F UV0..31/224..255 -> physical halfword x960..967/y224..255를 읽는다. 8번은 tpage0x1F UV32..63/192..223 -> x968..975/y448..479를 읽는다.
- 후자는 V323 이후 범위 커서 목적지 x960..984/y447..479 안에 완전히 포함된다. V345는 V341의 owner/active gate 기반 refresh 경로를 다시 활성화했다. 1/8번 owner=0x801F52BC, active필드=0이고 gate RAM은 현행 EXE와 같다.
- 목적지 전체1650B가 원본 COMM y128..160 첫50B씩으로 만든 범위 커서와 byte-exact. SHA B0005B318220FC61C11C3290837A7DF245646254FFA5CEBE7EA9A11932C7F421. 실제 읽는 부분을 CLUT0x7DCC로 렌더하면 사용자 사각 테두리가 나온다(tex_effect.png).
- 따라서 현재 증상의 직접 원인은 범위 커서 픽셀을 다른 비텍스트 프레임이 소비하는 VRAM 충돌이다. 과거 25상태에서 독자0이었던 목적지 안전 판정은 이번 장면에서 반증됐다. 원본 COMM 전체/한글 글리프/배경 DAT를 무작정 되돌릴 근거가 아니다.
- 새 위치 지정, 영역 지우기, 업로더 비활성화는 수행하지 않았다. 그러면 기존 정상 범위 커서가 사라질 수 있다. 마지막 업로드 타이밍을 새 실행에서 trace하거나 수정안을 A/B 검증한 결과는 아직 없으므로 수정 안전성/해결 완료를 주장하지 않는다.

증거: causes.json, cause_code.txt, runtime.json, frame1_0.png/frame8_0.png, tex_effect.png. 이 결과는 기존 문서의 잠정 `원인 미확정`을 갱신한다. 7번은 원본 みてみて 확인 결과 유지.

- 8개 입력 모두 DUCCV / 헤더 제목 V359_REVIEW_UPDATE2. SHA와 경로는 inventory.json. 첫 Zstd 프레임은 모두 256x192 BGRA 196608B이며 저장 화면을 추출했다. RAM 구조 호환성은 아직 검증하지 않았다.
- 기존 DUCCU 전용 parse_state는 버전 검사에서 정상적으로 거부했다. 버전 바이트를 바꾸어 강제 파싱하지 않고 독립 썸네일 프레임만 추출했다. 원본 세이브 수정 없음.
- 3: 파워 암이. 현행 EXE pointer 0x80AB0 -> 0x80DEA, 문장 `촌가라 방어력 30% 상승`. 구 원문 자료 ui_full_v42.csv equipment_description 7은 防御力が30…上昇します（チョン…ラ）. 문장체 생략은 있으나 30%/방어력/적용 인물 정보는 남아 있다. 설명창 높이/행간 문제와 문장 길이 문제는 분리한다.
