# 동적 캐시 자리 이동 — 확정된 사실과 배제된 경로

2026-08-14. v222~v229 여덟 판의 콜드부팅 결과에서 얻은 것. 다음에 이어갈 때
여기부터 시작하면 된다.

---

## 1. 문제의 정체

캐시 사각형 `x961..981, y480..491`은 **게임이 텍스처를 올리는 자리**다.
세이브 467장을 합집합으로 접으면 252 halfword 전부가 쓰인다.

피해 방향은 **게임 → 우리**다. 월드맵에 들어가면 게임이 자기 그림을 그 위에
로드하고, 번역 글자가 있던 칸에 그림 조각이 남는다. 반대 방향도 동시에 있어서
(v227에서 확인) 게임 구름 스프라이트에 우리 글자가 나타나기도 한다.

**v222가 자리를 옮기자 그래픽 침범이 처음으로 사라졌다.** 원인은 겹침이 맞다.

## 2. VRAM 점유 실측

`extract_savestate_vram.locate_vram`로 세이브 467장을 읽어 누적 OR.

```
미사용 halfword          13,869 / 524,288   (2%)
21x12 통째 미사용 사각형   2곳
    y415..426  x975..1023   연속폭 49
    y427..438  x999..1023   연속폭 25
```

가상 행 격자(`row * 12 = 절대 y`)에 맞는 것은 하나뿐이다.

```
row 35   y420..431   x999..1019     0 / 252    <= 유일한 후보
row 40   y480..491   x961..981    252 / 252    <= 현재 자리
```

x961 세로줄은 row 22~41 전부 게임이 쓴다. **v211이 x를 고정한 채 세로로만
찾았기 때문에 "빈 자리가 없다"는 결론이 나왔고, v212~v219의 A/B 선택자가
거기서 파생됐다.** 가로로 옮기면 후보가 존재한다.

### 표본 크기의 함정

같은 자리를 표본을 늘려 재면 계속 뒤집힌다. 이 프로젝트에서만 여섯 번.

```
strip C y380 / 빈 글꼴칸 140개 / 텍스처 페이지 5,0     (이전 세션들)
row 38·39      280장 0장  →  466장 21·23장
0x801A7051     120장 0B   →  486장 103B
```

**"표본에 안 잡혔다"는 "게임이 안 쓴다"가 아니다.** 위 row 35 후보도 467장
기준일 뿐이며, 진행률이 20%대라는 점을 감안해야 한다.

## 3. UV 생성 경로 — 확정과 배제

패킷 구조에서 `+0x28 = U`, `+0x29 = V`. 두 바이트가 인접해 있어
`lhu`/`sh`로 함께 다룰 수 있다(v228·v229에서 실제로 동작함을 확인).

### V — 확정

```
8016B59C  sll  v0, t0, 1
8016B5A0  addu v0, v0, t0
8016B5A4  sll  v0, v0, 2        v0 = row * 12
8016B5A8  sb   v0, 0x29(a1)     V = (row * 12) & 0xFF
```

`row 40 → 480 → 224`, `row 35 → 420 → 164`. 실측 일치.
`cache index base`(`row * 84`, 상주 decoder 안)를 바꾸면 V가 따라온다.

### U — 미확정

```
8016B588  sra  v1, a3, 2
8016B58C  sll  v0, v1, 1
8016B590  addu v0, v0, v1
8016B594  sll  v0, v0, 2        v0 = col * 12
8016B598  sb   v0, 0x28(a1)     U = col * 12          <= 기본값
```

정상 상태의 실측 U는 `4, 16, 28, 40, 52, 64, 76` = `col*12 + 4`.
즉 **캐시 글리프에만 `+4` 보정이 붙는다.** 그 지점을 세 번 짚었고 세 곳 다
아니었다.

| 후보 | 주소 | 결과 | 판정 |
|---|---|---|---|
| 원본 보정 블록 | `0x8016B5C4` (`bne v1,6` 뒤) | v225에서 +156 → 일반 글자까지 U 이동, 전면 손상. v228에서 lhu/sh 쌍 이동 → 패킷 U 불변(`4,16,28`) | **캐시 전용 아님. 실행 경로도 아님** |
| low helper | `0x801A2074` (`row==40` 문지기 뒤) | v229에서 lhu/sh 쌍 이동 → 원래 `V=72`인 글자가 `V=12`로 이동, 캐시 패킷은 `V=224` 유지 | **아틀라스 40행 일반 글자 경로** |
| cache index base | 상주 decoder | v222·v224에서 `35*84` → V는 164로 이동하지만 low helper의 `row==40` 판정이 깨져 U 보정 블록 전체가 미실행 | **V만 옮기고 U를 죽인다** |

**핵심 제약**: `index base`를 바꾸면 V는 따라오지만 캐시 판별이 깨진다.
V와 U를 동시에 만족시키려면 캐시에만 걸리는 별도 지점이 필요하다.

### 이미 검증된 사실

- **업로드는 이미 정확하다.** v228 세이브에서 새 사각형 `x999,y420`이 230/252,
  옛 자리 0/252. `upload_rect`와 `cache X`(decoder의 `addiu t0,t0,961`) 변경으로
  충분하다.
- 남은 것은 **읽기 좌표 하나**뿐이다.

## 4. 캐시 존재 판정 — 재업로드가 안 되는 이유

```
801FF488  lui  t5, 0x801f
801FF48C  ori  t5, t5, 0xf2fe      owners
801FF494  lhu  t7, (t5)            owners[i]
801FF49C  beq  t7, t4, 0x801FF53C  이미 있다 -> 업로드 건너뜀
...
801FF53C  ori  t0, zero, 1
801FF558  sw   t8, (t5)            active_mask 비트만 세움
```

캐시는 **`owners` 배열만 보고 존재를 판정한다.** VRAM 픽셀이 살아 있는지는
확인하지 않는다. `active_mask`는 교체 슬롯 선정에만 쓰인다.

- v226: `LoadImage` 후크로 `active_mask`를 0으로 만들었다. 후크와 마스크 0은
  세이브에서 확인됐으나 `owners`가 남아 재업로드되지 않았다.
- v227: `0x801FF49C`를 nop으로 만들어 매 프레임 재업로드하게 했다. 월드맵
  이전은 정상이었으나, 자리가 겹친 상태에서는 게임과 번갈아 덮어써서 화면이
  불안정하다. **재업로드로는 겹침을 이길 수 없다.**

## 5. 코드 공간 — 전부 배제됨

| 자리 | 크기 | 판정 |
|---|---|---|
| `0x801A9BD8` | 1064B | 486장에서 전부 사용 |
| `0x801A7051` | 103B | 120장 0B → 486장 103B |
| 상주 아래 `0x801FE1B0` 등 | 44B x 4 | 규칙적 간격, 배열의 빈 필드로 보임 |
| 문자열 풀 87B 구간들 | 87B x 5 | 미사용이 2B 단위로만 흩어짐 |
| `LoadImage` 내부 | — | `s0`~`s4` 전부 실제 사용 |
| 상주 영역 | 5356/5356 | 여백 2B |

**표본으로 찾은 빈 자리는 신뢰할 수 없다.** 확실한 자리는 상주 블록에서
떼어내는 것뿐이다.

v226에서 실제로 확보한 방법: 캐시 슬롯 28→20으로 줄이면 `owners`가 56B→40B가
되어 `0x801FF328..0x801FF337`(16B)이 남는다. **배열을 옮길 필요가 없다** —
코드가 뒤 8칸을 안 쓰게 되는 것뿐이다. `CACHE_N` 상수 4곳과 `CACHE_CELLS` 2곳,
총 6개 워드가 상주 안에 각각 정확히 한 곳씩 있다.

## 6. 다음 수

후보를 추측으로 하나씩 태우는 방식은 오늘 세 번 실패했다. 대신:

1. 세이브에서 **캐시 패킷 하나를 특정한다** (`V=224`이고 `U`가
   `4,16,28,...` 중 하나인 12x12 SPRT).
2. 그 패킷이 놓인 OT 주소에서 **누가 그 halfword를 기록했는지 역추적한다.**
3. 그 지점이 캐시에만 걸리는지 확인한 뒤, v228·v229에서 검증된 lhu/sh 쌍
   이동을 적용한다. `DELTA = 156 + (-60 << 8) = -15204 = 0xC49C`.

U 156~228은 x999~1017, V 164는 y420이며, 둘 다 바이트 안에 들어가 캐리가 없다.
`upload_rect`와 `cache X`는 이미 맞춰져 있다.

## 8. 추가 발견 — U 보정의 실제 지점 (같은 날 저녁)

`sb ?, 0x28(?)`를 EXE 전체에서 훑었다. 18곳 중 직전에 `+4`를 하는 곳은 셋이다.

```
0x8016B5C8   직전 addiu v0,v0,4     v225/v228 시도 -> 실패 (실행 경로 아님)
0x8019D0C0   직전 addiu a3,a3,4     <= 실제로 도는 자리
0x801A2078   직전 addiu a3,a3,4     v229 시도 -> 실패 (아틀라스 40행 일반 글자)
```

`0x8019D0C0`은 글리프 패킷 훅 `0x8016B5D8`이 `j 0x8019d074`로 뛰어드는 블록
안이다. v171이 만든 코드이며, 오늘 여덟 판 내내 후보에 없었다.

```
8019D074  addiu a3, t0, -0x28    행 40 (CACHE_ROW)   ┐
8019D084  addiu a3, t0, -0x3f    행 63               │ 넷 중 하나면
8019D094  addiu a3, t0, -0x35    행 53               │
8019D0A4  addiu a3, t0, -0x34    행 52               ┘
8019D0AC  beqz  a3, 0x8019d0c4   아니면 건너뜀
8019D0B4  lbu   a3, 0x28(a1)
8019D0BC  addiu a3, a3, 4        <= U 보정
8019D0C0  sb    a3, 0x28(a1)
8019D0C8  j     0x8016b5e0
8019D0CC  nop                    (j 의 delay slot -- 덮으면 안 됨)
```

### 제약

캐시 행 40이 63/53/52와 보정 블록을 **공유한다.** 블록을 통째로 lhu/sh 쌍
이동으로 바꾸면 나머지 세 행의 글자도 함께 움직여 v229와 같은 손상이 난다.
행 63/53/52의 용도는 아직 확인하지 않았다. `v171`/`old`의 정수 상수 중 52·53·63과
일치하는 것은 없다.

### 남은 작업

행 40만 전용 블록으로 분리해야 한다. 명령 수 계산:

```
현재   검사 4개 x 4명령(addiu/sltiu/bnez/nop) = 16
       공통 보정 4명령 + 마무리 3명령          =  7
                                          합계  23명령 (0x8019D074..0x8019D0CC)

필요   검사 4개 x 3명령 (delay slot 에 다음 addiu 를 넣어 nop 제거) = 12
       행40 전용 4명령 (lhu/nop/addiu/sh)                          =  4
       행63/53/52 공통 4명령 (lbu/nop/addiu/sb)                    =  4
       마무리 3명령                                                =  3
                                                              합계  23명령
```

**블록 크기 안에서 재배치가 가능하다.** 새 코드 공간은 필요 없다.
`0x8019D0CC`는 `j 0x8016b5e0`의 delay slot이므로 반드시 보존한다.

적용할 값은 v228/v229에서 이미 검증된 것과 같다.

```
lhu   a3, 0x28(a1)
addiu a3, a3, -15204      (0xC49C)   U +156, V -60
sh    a3, 0x28(a1)
```

`U = col*12 + 156` -> 156..228 -> x999..1017,  `V = 164` -> y420.
둘 다 바이트 안에 들어가 캐리가 없다. `upload_rect`와 `cache X`는 v228에서
이미 정확함이 확인됐다(새 자리 230/252, 옛 자리 0/252).

### 착수 전 확인할 것

1. 행 63·53·52가 무엇인지. 캐시와 같은 VRAM 영역을 쓴다면 분리 없이 블록
   전체를 옮겨도 되고, 그러면 3바이트로 끝난다.
2. 분리가 필요하면 위 재배치를 적용한다.

## 9. 상주 스트립과 캐시는 같은 좌표다

`extract_savestate_vram`의 스트립 상수와 캐시 좌표가 일치한다.

```
STRIP_A_XY  = (961, 480)      <= 현재 동적 캐시 사각형과 동일
STRIP_B_XY  = (961, 500)
캐시         =  x961..981, y480..491
```

캐시는 자리를 새로 고른 적이 없다. v160이 고정 스트립 업로드를 없애면서
**스트립 A의 좌표를 그대로 물려받았다.** 지금 겪는 겹침은 스트립 시절부터
있던 자리를 이어받은 결과다.

세이브 508장에서 두 자리의 내용을 재면 성격이 뚜렷하게 갈린다.

```
A (961,480)   빈칸 45%   일부 51%   꽉참  3%
B (961,500)   빈칸 78%   일부 21%   꽉참  0%
```

**B는 게임 텍스처가 통째로 올라온 적이 한 번도 없다.** A의 꽉참 3%가 월드맵이
우리 글자를 지우는 순간이다. 스트립 B도 같은 세로줄에 있어 안전하지는 않지만,
빈도가 크게 낮다.

주의: 이 측정은 우리 스트립·캐시 픽셀과 게임 픽셀을 구분하지 못한다. 가르려면
패치하지 않은 원본 실행의 세이브가 필요하며, 현재 없다. 다만 v222에서 캐시를
비운 뒤에도 옛 자리가 252/252로 찬 세이브가 있었으므로 게임이 그 칸을 쓴다는
것 자체는 확정이다.

## 10. 캐시 크기와 자리 개수 — 축소의 실익

467장 누적 지도에서 크기별로 "한 번도 안 쓰인" 사각형을 셌다.

```
슬롯   셀   폭     통째로 빈 자리      행격자(y=row*12) 정렬
 28     7  21칸        18곳                 1곳  (row 35)
 20     5  15칸        27곳                 3곳  (row 35, 36)
 16     4  12칸        41곳                 3곳
 12     3   9칸        54곳                 4곳
  8     2   6칸       114곳                10곳  (row 32, 35, 36)
  4     1   3칸       330곳                26곳
```

28슬롯에서는 행격자에 맞는 후보가 **단 하나**다. 그 하나가 나중에 뒤집히면
대안이 없다. 8슬롯까지 내려가면 10곳이 되어 표본 함정에 대한 내성이 생긴다.

### 그런데 축소의 대가

세이브 508장에서 한 화면이 동시에 쓴 캐시 셀 수를 셌다.

```
셀 0개 (동적 글자 없음)   284장    누적  55%
셀 1~4개                   46장    누적  64%
셀 5개 (20슬롯)            21장    누적  69%
셀 6개 (24슬롯)            63장    누적  81%
셀 7개 (28슬롯, 현재)      94장    누적 100%
```

**7셀을 꽉 채우는 화면이 94장, 19%다.** 슬롯을 20개로 줄이면 화면의 31%에서
글자가 밀려나고, 밀려난 자리에는 엉뚱한 글자가 그려진다. 자리를 얻고 글자를
잃는 교환이므로 단독으로는 이득이 아니다.

### 두 축을 함께 줄이면 성립한다

`캐시 슬롯 수`(VRAM 크기를 결정)와 `동적 글자 종류 370개`(상주 데이터 크기를
결정)는 별개 축이다. 종류를 줄여도 VRAM 점유는 그대로지만, **7셀을 채우는
19%의 화면은 희귀 글자가 몰린 대사들**이므로 그 대사의 문구를 흔한 글자로
바꾸면 셀 요구가 내려간다.

```
번역 문구 조정 -> 화면당 동적 글자 감소 -> 슬롯 축소 가능 -> VRAM 자리 확보
```

착수한다면 먼저 7셀을 요구하는 대사 목록을 뽑아 그 수를 세야 한다. 아직 세지
않았다.

## 11. v230 방향 — 같은 열, 한 행 아래

오늘 여덟 판의 실패 원인은 전부 U였다. 세로로만 내려가면 x와 U 경로를 아예
건드리지 않는다.

```
cache row   40 -> 41
upload y   480 -> 492
V          224 -> 236
x, U             변경 없음
```

row 41(`y492..503`)은 466장 중 94장이 쓴다. 현재 row 40의 264장에서 3분의 1로
줄어든다. 완전한 해결은 아니지만 U를 건드리지 않는 유일한 개선 경로다.

편집 대상은 다섯 곳이다. `cache index base`(40*84 -> 41*84), `classifier V`,
`frame V`(-224 -> -236), `upload_rect` y, 그리고 U 보정 블록의 행 판정
`0x8019D074`(-40 -> -41).

### 빌드가 막힌 지점

`build_arc1_v230_claude_row41_same_column.py`가 가드에서 멈춘다.

```
U bias row test: 0x2507FFD7, expected 0x2507FFD8
```

`0x8019D074`의 파일 오프셋을 독립적으로 읽으면 `0x2507FFD8`(-40)로 정상이다.
빌더 안에서만 `-41`이 읽힌다. `v190.resident_layout()` 호출 이후 `old.file_at`의
기준이 달라지는 것으로 보이며, 직접 계산(`addr - 0x8011A800`)으로 바꿔도 같은
값이 나온다. 즉 오프셋 문제가 아니라 **가드 지점 이전에 `exe`가 이미 수정되고
있다.** 다음에 이어갈 때 여기부터 보면 된다.
