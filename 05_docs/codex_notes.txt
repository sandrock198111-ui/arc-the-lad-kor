PSX dialogue glyph decoder and COMM bitplanes - 2026-07-13
- The verified decoder routine is around PSX address `0x8016B3C0`. A byte below `0xDD` consumes one byte and maps to glyph index `byte - 1`.
- Prefixes `0xDD-0xE0` consume a second byte and map to glyph index `(first - 0xDD) * 255 + second + 0xDB`.
- The renderer around `0x8016B518` maps an index with `row, rem = divmod(index, 84)` and `column, plane = divmod(rem, 4)`.
- Each `COMM.IMG` pixel nibble contains four independent 1bpp glyph planes. Writing nibble value `0xF` corrupts three neighboring glyphs and explains the failed earlier two-byte font experiments.
- Correct font writing sets or clears only `1 << plane` while preserving the other three bits.
- Ninety-four `E0 xx` codes selected by `korean_charmap_extended.csv` do not occur in the baseline story DAT script regions at and after file offset `0x45000`.
- `build_story_sf0b1_return_full.py` verifies source bytes, boundaries, code non-use, glyph plane isolation, and cumulative-file preservation before producing the ZIP.

Battle cursor / COMM texture collision - 2026-07-13
- DuckStation's final decompressed state frame stores PS1 VRAM at state offset `0x202000` for the current build. VRAM is 1024x512 16bpp and occupies `0x100000` bytes.
- `COMM.IMG` is uploaded as 896 bytes per source row into VRAM rows with 2048-byte stride; the observed first-row placement is state offset `0x202058`.
- Enemy-turn cursor commands sample a 16x16 shared texture around `UV=(32,160)` and another animation row. With the current COMM placement, the corrupted strip corresponds to font columns 9 and 10.
- A code being unused in story DAT files does not prove its glyph cell is safe: non-text battle graphics can sample the same COMM texture cells directly by UV.
- Extended font allocator rule: never assign a glyph to columns 9 or 10. The SF0B1 builder enforces this through `CURSOR_RESERVED_COLUMNS`.
- Fourteen mappings formerly in these columns were moved. The cursor columns in the rebuilt COMM are verified byte-for-byte against the accepted pre-extension cumulative base.

E2 inline return termination - 2026-07-14

Dialogue glyph spacing structure - 2026-07-14
- `0x8016B518` is the common glyph sprite builder. Text-state byte `+0x0D` becomes sprite width, byte `+0x0E` becomes height, byte `+0x0F` is extra horizontal spacing, and current X at `+0x06` advances by `+0x0D + +0x0F`.
- Automatic horizontal wrapping at `0x8016BA18-0x8016BA3C` compares the current relative X plus the same width/spacing sum against state limit `+0x22`.
- Dialogue inline glyphs enter the builder at call `0x8016BB8C`; E2 secondary glyphs enter at `0x8016BDA0`. Redirecting only these calls permits dialogue-specific spacing without changing unrelated UI callers.
- Space code `0x9C` decodes to glyph index `0x9B`. A dialogue wrapper can select a 6-pixel blank sprite for this index and 11 pixels for other dialogue glyphs.
- Reducing advance alone is unsafe: 76 of the 356 measured Hangul glyphs occupy 11 or 12 source columns. Their mapped font planes must be shifted or narrowed into the selected source width before runtime use.
- v0.7 narrows only mapped bitplanes and preserves every neighboring plane plus the confirmed battle-cursor rectangle. Runtime legibility remains a required acceptance test.
- The earlier v0.7 wrapper run at game 0 FPS is not a valid wrapper rejection: it used a long-lived DuckStation process affected by prior GDB attachment. Keep the wrapper unaccepted, but require a fresh no-GDB process before assigning runtime fault to its code.
- Safer dialogue-only width point: global dialogue state `0x801F1DB4` is initialized through `0x8016B134` and reset through `0x8016C4D8`. Four reset calls have empty delay slots, and the reset return delay slot is also empty. Passing width in `v0` and storing it to state byte `+0x0D` changes dialogue width without touching common glyph draw calls or unrelated text-state initializers.
- Rejected v0.8 presentation: setting state width 11 also crops the generated sprite to 11 source pixels. Repositioning mapped planes did not preserve every wide Hangul shape; `하` lost a rightmost stroke. Keep glyph sprite width 12.
- Space code `0x9C` decodes to index `0x9B` before `0x8016B518`. Register `t1` is unused by the original builder, and original instruction `0x8016B524` is `nop`, so it can safely retain this comparison index through the function.
- The original advance tail has enough instructions to select 6 for index `0x9B` and retain state width for every other glyph without a wrapper or code cave. This changes X advance only; sprite width and font pixels remain untouched.
- Missing-leading-glyph appearance after an expanded line can be an inline-tail symptom rather than a font failure. If `E2 nn` replaced the first original glyph and completion skipping fails, the resumed old text naturally begins at its second glyph. P6 pass classification must be per packet, not global state - 2026-07-31
- The glyph packet array is a 52-byte-stride array shared by the common glyph builder at `0x8016B518` and the E7 icon builder at `0x8016B668`. Both write U at `+0x28`, V at `+0x29`, W at `+0x2A`, H at `+0x2B`, X at `+0x2C`, Y at `+0x2E`, and CLUT at `+0x30`. Bytes `+0x32` and `+0x33` are spare.
- Each packet also carries two 20-byte `SPRT` primitives at `+0x00` and `+0x14`; the driver selects one with `s4 = framebuffer_parity * 20`.
- `SPRT` has no tpage field. - The classification input is already per glyph. `0x8016B5A8` stores `V = row * 12` with `sb`, so row 24 truncates to 32, and `24*12 - 256 = 32` is simultaneously the correct within-high-page V. Among valid rows 0-42, only row 24 yields V == 32.

- Do not generalize this to `V % 12 != 0`. E7 icons use V = 130, which is not a multiple of 12 and would be misclassified as high page. Exact comparison against 32 is safe because 130 and 228 are both different from 32.
- The `U += 40` applied by the glyph helper is required for P6 cells and must be preserved by any replacement.

High-page tpage arithmetic - 2026-07-31
- For 4bpp, texture page N begins at VRAM x4bpp N*256. The tpage word holds tx in bits 0-3, ty in bit 4, abr in bits 5-6 and colour depth in bits 7-8.
- `andi a3,a3,0xFFE0` clears tx as well as ty. Preserving abr and colour depth while replacing both tx and ty is intentional, but the replacement must supply tx, not only the ty bit.
- The base tpage at `0x801F2FFC` is `0x0005` in 107 of 108 inspected savestates, so low-page glyphs live in page 5 and P6 in page 11. P6 pixels sit at a fixed VRAM location, so the high-page tx must be a constant and must not be derived as base+1.

Text-object struct is exactly 68 bytes with no spare room - 2026-07-31

- `0x801F9D44` and `0x801F9D88` are 68 bytes apart, so the struct is exactly 68 bytes.
- The initializer fills header fields `0x00-0x10`, then the loop at `0x8016B178` starts at s0 = 44 and steps by 12 while s0 < 68, building two 12-byte low-page `DR_TPAGE` primitives at `+44` and `+56`. Bytes 0..67 are therefore fully used.
- Conclusion: the two existing tpage slots are already committed to the low page, and the struct cannot hold two more for the high page. Do not plan on extending it.
- Memory layout per text object is `[packet array of limit*52 bytes][68-byte header]`, verified three times: `0x801EFC9C + 32*52 = 0x801F031C`, `0x801F0798 + 32*52 = 0x801F0E18`, `0x801F1A74 + 16*52 = 0x801F1DB4`. LoadImage: available, and where it can be called - 2026-07-31
- Psy-Q `LoadImage` is linked at `0x80177E4C`. It takes a0 = RECT (short x, y, w, h in 16-bit units) and a1 = source pointer, and clamps to the 1024x512 VRAM bounds.
- It waits for the GPU itself: the loop at `0x80177FC4-0x80177FF0` spins on `GPUSTAT & 0x04000000` with a timeout call to `0x80178CCC`. Callers do not need their own synchronisation, but they must not call it while the GPU is busy.
- v99 hooked the text-render entry `0x8016B764` and deadlocked. The savestate showed `s6 = 0x80177E4C`, `ra = 0x80177FD0` and `s2 = 0x04000000`: the CPU sat in LoadImage's own wait loop while the frame it was blocking could never finish, so sprites stopped being drawn. Never call LoadImage from the render path.
- v100 hooked the frame loop instead and runs normally. The usable point is `0x8011C4AC`, the `jal 0x8011C814` that performs the frame swap. `0x8011C49C` calls the GPU driver's sync entry with a0 = 0 immediately before it, so the GPU is idle between the two.
- `0x8011C814` is the frame swap and the only writer of the buffer parity at render-context `+0x870`; roughly sixty other sites only read it. `0x801F12EC` holds the render-context pointer.

Heap is too small to host the glyph source - 2026-07-31

Glyph strip placement rules - 2026-08-02
- The renderer emits one DR_TPAGE per text object at `0x801A2188..0x801A2198`, but U is written per glyph by the helper into packet byte `0x28`, and V per glyph as `(row * 12) & 0xFF`. A strip anywhere inside the page the objects already select therefore costs only one more row test in the helper, one more V test in the classifier, and one more LoadImage in the frame routine. A strip outside that page would need a tpage primitive per glyph.
- V must be a multiple of 4 and must avoid the 24 values the base rows produce: the multiples of 12 from 0 to 252, plus 8 and 20. The family V = 4 (mod 12) is clear, and its spacing of 12 matches the strip height so bands do not overlap.
- At x 960 the U offset is 0, so a band holds up to 21 columns (252 of the page's 256 pixels), which is 84 glyphs.
- Reserved RAM, not VRAM, is the binding limit: 18 bytes per glyph, 2520 bytes available above the v118 heap base, so at most 140 further glyphs without moving the heap again.

E2 external slot mechanism, consolidated - 2026-08-02
- Assembled from notes scattered across codex_notes, test_log and changelog because quoting a partial version of this produced a wrong capacity claim twice in one session. Read this entry, not the older fragments.

- Layout. A scene file reserves 0x45000..0x477FF, ahead of dialogue bodies that begin near 0x47800. That is 79 complete 128-byte slots. Slot n is at file offset 0x45000 + n * 0x80. The file-to-RAM delta is +0xCF000, so slot 0 is RAM 0x80114000; the address formula is 0x80114000 + slot * 0x80, and the earlier 0x80110000 + slot * 0x80 was wrong because it omitted the 0x4000 bank displacement.

- Disk IDs. 81-A8 select slots 0..39 and AA-D0 select slots 40..78. **A9 is reserved: the original parsed dialogue already uses it.** So the 80 IDs in 81..D0 yield 79 slots, not 80. This is the one that goes missing from the expansion.
- The lookup receives the decremented internal ID. Low slots map internal - 0x80, high slots map internal - 0x81; completion maps disk - 0x81 or disk - 0x82. The one-step shift across A9 must be applied in both the lookup and the completion path, or the slot resolves one place off.

- Per-slot cost. Byte 0x7F of each slot holds the completion metadata, `original capacity - 2`, and the text is zero-terminated before it. Usable text is therefore under 128 bytes per slot, not 128.

- What cannot go in a slot. `E6 01` is not interpreted inside a secondary string and renders as visible garbage; use spaces and let the renderer wrap. The four S3032 blocks at 0x45000..0x45180 each carried two `E6 01` and showed a garbled glyph at exactly those positions.
- A body that mixes prose with `E5` choices must not use `capacity - 2` metadata, because that skip would swallow the choices. For S3012 0x47FF0, E2 replaces only the prompt and the option text stays inline within its original capacity.

- Allocation is per file, not global. Some scene files use part of the nominal bank for real data, so a builder must test each 128-byte slot in the actual cumulative file and take only fully zero ones. S1072's sixteen were empty; that is a measurement of one file, not a rule.

- Separately, the battle-icon work removed capacity of a different kind. Relocating the E7 confirm/cancel icons consumed two charmap-unassigned 12x12 font cells, and the recorded canaries that later builds must not disturb are the v0.39 0x6C LV plane, the E7 icon rectangles, the battle-cursor region, five HUD special payloads, 17 Japanese-preserved rows, and all story members. E7 icons sit at V=130 and, after relocation, IDs 2 and 3 at U=180/192 with V=228. Any classifier that tests V by exact value must avoid 130 and 228; a `V % 12` test would misclassify them.

- The documented repair is one E2 call per non-empty source text row, each slot's skip ending immediately before that row's original E6, so the inline parser still executes the break. For a single-row prompt followed by E6, keep one command and shorten the skip to `row_end - row_start - 2`.
- That repair cannot be applied mechanically to this corpus. Of the 1,292 affected bodies only 14 have a `|` count in the Korean matching the source E6 count; 1,278 disagree, and 1,277 of those are Korean with no `|` at all against a source of one to six rows. The translation was written as flowing sentences, so the row structure it must be poured back into no longer exists in it.
- The 508 bodies with no E6 in the source were always safe and are the only part of v121 that can be kept as built.
- Separately: untranslated Japanese still on screen is not a font fault. The font keeps 17 Japanese rows by design, and any body not yet replaced renders from them. The reported line, `32/S3051.DAT 0x48D62`, is translated in the table but was one of the 484 the planner left out.

Put rules in the builder, not only in this file - 2026-08-02
- Four regressions in one session repeated something already written down: the blank-plane trap (v109, v111, then v118 and the START icon), the E2 slot count, the E6 skip rule, and the instruction to find the first build that shows a symptom before theorising. In every case the answer was in the documents and the build was made first.
- A rule kept only as prose depends on someone reading it at the right moment, and reading it far enough. Both failed here, twice each.
- Where a rule can be checked mechanically, the builder should check it and refuse. `cell_is_occupied` in the v118 builder now makes the blank-plane mistake unbuildable; the E6 guard in `plan_bulk_insertion.py` does the same for the skip rule. Prefer adding a guard over adding a paragraph.
- A guard is also self-documenting at the moment it matters: it fails with the reason, at the point of the mistake, instead of waiting for a screenshot.

A rule stops new defects; it does not remove old ones - 2026-08-02
- `E6 01` inside an E2 secondary string is drawn rather than obeyed and shows as one squashed glyph mid-sentence. That was established 2026-07-15 and every builder since has honoured it.
- The archive still carried 38 slots holding 54 of them, written before the rule existed. They were still on screen in v119. The user found one in `32/S3051.DAT` slot 63, between the fourth and fifth syllables of a sentence, and recognised it as a defect that had already cost a lot of work.

- Writing the sweep hit the trap the rule warns about in its own right: scanning for the byte 0xE6 rather than for the token `E6 01` found 24 false positives, because 0xE6 also occurs as the second byte of a two-byte glyph. Walk the stream -- 0x01..0xDC one byte, 0xDD.. two bytes -- and judge a byte only at a token boundary.

Glyph index 179 was ベ on a guess; it is 恵 - 2026-08-02

Verifying a build somebody else made - 2026-08-04
- Check the claim against the artifact, not against the report. Two claims in the v127/v128 reports did not survive that: the rect table appears to hold only three strips because the fourth rect lives in reserved RAM at 0x801FF834, and the classifier at 0x801FEC28 still tests three V values because the live one was relocated to 0x801FE420. Relocation needs a coverage check, not a read-back check - 2026-08-04
- When glyphs are moved out of a region so the region can be restored, verifying that the moved ones read back at their new address proves nothing about the ones that were missed. Enumerate the region first, then require every live plane in it to have a destination.
- v127 moved 46 planes out of the skill-range cells and left 러 and 뜨 behind. Both had ink in v126, both are common, and 뜨 had no second home, so it became undrawable. 534 occurrences in the shipped archive.
- The check that finds this: for each plane in the region, does the v126 bitmap name a character, and does the remap table give it a destination? A character on one side and FF on the other is the defect.

The strip D remap ABI, and how to add to it - 2026-08-05
- The remap table at `0x801FF7F4` is 64 bytes, one per plane of the 16 restored skill-range cells, indexed `(row-10)*16 + (col-2)*4 + plane`. 0xFF means leave the cell alone; anything else is a strip D slot.
- The lookup at `0x801FE4A4` returns `slot + 4368`. 4368 is 52*84, so the slot is simply re-expressed as row 52 of the font page and every downstream U/V calculation is the ordinary one. There is no per-strip special case to update when adding a glyph.
- A strip is 936 bytes, 78 per row, which is 156 4bpp pixels: 13 columns of 12, so 52 slots as `col*4 + plane`. The rects confirm it -- strip D's is (961, 368, 39, 12) and 39 halfwords is those same 156 pixels. Column 12 is real and strips A, B and C all use it.
- So adding a glyph to a strip is two writes: the 12x12 plane into a free slot, and the slot number into the table. Take the bitmap from the last build that still held it rather than re-rendering, so the diff stays provably minimal.

The font spans two texture pages, and only the classifier can cross - 2026-08-05
- The font sits at VRAM page x=5 and runs from y=0 to y=467, so font rows 0..21 are on texture page (5,0) and rows 22..39 are on (5,1). V is `(row*12) & 0xFF` and is correct for both halves; what distinguishes them is the texture page, and the texture page is chosen per glyph by the classifier.
- The classifier only recognises the four resident strips by their V values. It has no test for "ordinary font row on the second page", so every non-strip glyph on rows 22..39 draws from page (5,0) at the same U and V: right position on screen, wrong twelve rows of pixels. On screen it reads as one character vertically smeared into its neighbour.
- This is why the V selection rule for a new strip says to avoid 8 and 20: those are rows 22 and 23, the first two rows of the second page.
- The encoder must never hand out a physical code whose row is 22..39 unless that row is a strip. Prefer the strip code; every one of the 25 characters that had this problem already had a correct twin in strip A. Put the check in `build_encoder`, not in a comment.
- How to prove a glyph defect of this shape in one step: take the 12x12 ink mask off the framebuffer and search the whole VRAM for it. One exact hit gives the page, U and V the renderer actually used, and comparing that against the glyph's real location says whether the fault is U, V, the page, or the data.

An external slot holds 126 bytes of text, not 127 - 2026-08-05
- The slot is 128 bytes: text, a 0x00 terminator, then the `capacity - 2` completion-skip metadata in byte 0x7F. A 127-byte payload leaves no room for the terminator, and the metadata write then lands on byte 127 anyway, so the string never ends and the renderer walks into the next slot. It hangs.
- `SLOT_TEXT_MAX` must be 126. It was 127 and seven slots shipped without a terminator.
- The guard to add is not on the payload length but on the result: after writing a slot, require a 0x00 in bytes 0..126. Length arithmetic is what got this wrong in the first place.

An E2 slot inherits the original line's window, and cannot grow it - 2026-08-06
- The dialogue window is 21 cells wide, and how many rows it has is decided by the line breaks in the ORIGINAL body, not by the replacement text. A slot whose Korean needs more rows than the original had draws until the window is full and then stops; the game does not recover.
- So the budget for an E2 line is `(original E6 01 count + 1) * 21` cells, counting every glyph and every space as one cell. Check it in the builder and show it in the editor; it is a harder limit than the 126-byte slot size and it bites first.
- E6 inside a slot is drawn, not interpreted, so line breaks cannot be used to control the wrap. Shortening the text is the only lever.
- Save state 6 froze on `21/S2041.DAT 0x485A6`: three rows of window, 66 cells of Korean, 63 cells drawn.

Do not write Korean into a font cell that already has ink - 2026-08-06
- 398 original glyph planes were overwritten across the project's history. The original script still points at 115 of them 334 times, and 46 of those uses are in Japanese lines nobody has translated, so they draw a Korean syllable mid-sentence today.
- The two the user noticed are L at index 825 and R at index 732, the button labels in `LRボタン`. They cannot be written back into the Korean text either, because the codes now draw Korean.
- `cell_is_occupied` exists in the v118 builder and looks at all four planes of a cell. The rule it encodes was never applied to the font page as a whole. Before writing any font cell, require the plane to be empty on the ORIGINAL disc, not merely empty in the current build.

Measure the wrap, do not count characters - 2026-08-06
- A row is 228 pixels. A full-width glyph advances 12 and the space 0x9C advances 6, so a line with many spaces fits more than a character count suggests. Both numbers came off the framebuffer of save states, not from reading the code.
- The window is `max(original rows, 3)` rows tall. It is never shorter than the Japanese needed and never shorter than three.
- Counting tokens as uniform cells produced 196 false warnings against 9 real ones. When a user says a line looked fine in game, that is data: check the model before defending it.

The code space is one continuous index, and all of it is glyphs - 2026-08-06
- `index = code - 1` for a one-byte code 0x01..0xDC. The two-byte range picks up exactly where that ends: `(lead - 0xDD) * 255 + trail + 0xDB`, so `DD 01` is 220 and the one-byte range stops at 219. E9/EA go through the lookup table. There is no separate ASCII region and no reason to hardcode one.
- 118 of the 220 one-byte codes hold Korean. The encoder ignored them for the whole project because someone once wrote `{chr(i + 32): bytes((i + 1,)) for i in range(26)}` and nobody enumerated the rest. 괄, 량 and 덕 were being reported impossible while the game drew them.
- Identify a glyph by its picture, never by a name in a table. For anything the Hangul render table cannot name -- Latin, punctuation, icons -- take the cell off the ORIGINAL disc and look for that exact 12x12 in the build. A letter that was overwritten then fails to resolve on its own, with no special case and no guess.
- When the user says the game draws something the tool calls impossible, the tool is wrong. That has now happened three times in one session: the row budget, the H and P of HP, and 괄 량 덕.

Place and country names live in PSX.EXE, not in the script - 2026-08-06
- The save/load screen draws a country name from a pointer pair at file 0x81EE8 and 0x81EEC: 스메리아 at 0x820AC and 밀마나 at 0x781B1. Neither is in any DAT and neither is in the memory card, so renaming a country in the CSV can never change that screen.
- Two more strings carry the same name: 0x8194D `밀마나 공항` and 0x81A8E `밀마나 군본부`, in the place-name table that runs from about 0x818A2 to 0x81B40. Every entry there is 0x00-terminated and reached through a pointer.
- Because they are pointer-referenced, a longer name does not have to fit in place: move the string to free space and rewrite the one pointer. 밀마나 is three syllables and 미르마나 is four, so each of the three strings grows by two bytes and cannot be edited where it stands.
- Search for a name by walking tokens, not by matching the encoder's preferred bytes. The same syllable has several codes -- these tables use E9 lookup codes where the encoder would emit E0 -- and a byte search finds one table and misses the others. Require the match to begin just after a 0x00 or a mid-token alignment will invent hits.

Choice bodies: geometry first, redirect second - 2026-08-07
- Keep every E5 and E6 at the byte offset the original put it. Compare by offset, not token by token: Korean and Japanese use different token widths so the two streams fall out of step and a marker lines up against a glyph.
- A span too small for its Korean does not need the Korean shortened. Put E2 plus the disk id at the span start, fill the rest of the span with the space glyph, and set the slot metadata to span length minus two so completion resumes at that span's own marker. A span never contains an E6, so the rule against skipping a line break does not apply.
- E2 is a glyph lead as well as a command. E2 EB is 링, E2 DE is 띠. A phrase carrying one goes to a slot even if it would have fitted inline, because inside a body the renderer cannot tell them apart. Inside a slot it can: controls are not interpreted there.
- The CSV writes menu options with a bar; the disc writes them with a line break and a choice marker. Comparing without normalising that reported 201 lines as missing while the game was drawing them.
- A bar count that is one short is almost always the speaker: the original keeps 초핀 on its own row and the CSV wrote the speaker and the question as one phrase. One leading bar too many is the other habit. Those two rules realign 109 of 124.

One-byte codes are the cheapest capacity in the project - 2026-08-07
- index = code - 1 for 0x01..0xDC, and the two-byte range continues at 220, so the space is continuous. A syllable in a low cell costs one byte instead of two.
- Which cells are free is measured over rendered text only: pointer-referenced UI strings, inline bodies, and slot contents. Never count the Japanese tail an E2 body skips -- that says 217 of 220 are locked and kills the idea. Counted properly, 86 were free.
- Cost: those cells held Japanese kana, so untranslated lines get worse. They were already bad; 123 had been overwritten before this.

Do not translate the 199 untranslated lines - 2026-08-07

- Writing Korean into them overwrites data the game reads. Leave them.

When a line is blocked for want of a slot, do not shorten it - 2026-08-07
- Shorten whichever line in that file is cheapest to shorten. A line that fits where the Japanese sat needs no slot, so each one moved frees a slot for another.
- 212 blocked lines needed only 186 moves, across five files: C2/SC0B6, 6/S6054, 31/S3014, D/SD031, 32/S3051. Half were short by one or two bytes.
- Close a space before dropping punctuation, and never drop the exclamation or question mark -- they carry tone. Dropping a full stop is usually invisible.

실행파일 문자열은 두 갈래로 깨진다 - 2026-08-08
- 추출되지 않은 문자열은 번역도 이전도 되지 않는다. 포인터가 원본 주소를 그대로 들고 있는데, 재배치가 그 자리를 다른 한국어로 덮으면 포인터는 문자열 한가운데를 가리킨다. 화면에는 앞 글자 한 자가 다른 글자로 바뀌고 뒤가 이어져 나온다. '2음의 문번 그라운드를 배웠다'가 그것이다.

- 고칠 때는 덮어쓰지 말고 예약 블록 뒤 빈 자리(파일 0x8F3D8~0x8F800, 1064바이트)에 새로 쓰고 포인터만 다시 쓴다. 커서는 마지막 비영 바이트 + 2. 뒤에서 0을 건너뛰면 종결자 위에 선다.

실행파일 문자열은 한 벌이 아니다 - 2026-08-08
- 같은 음절에 철자가 여럿이다. 마는 한 바이트 0xD4, 넓은 범위 0xE0 0x9E, 조회표 0xE9 0x52. 그래서 바이트로 찾으면 못 찾는다. 포인터를 훑어 대상을 디코드해서 찾아야 한다.
- 고칠 때는 그 문자열이 원래 쓰던 공간으로 다시 쓴다. 세이브 화면은 넓은 범위, 지명표는 조회표를 쓴다.
- 0xE2 선두로는 적지 않는다. 대사에서 0xE2는 슬롯 리다이렉트다. UI 풀에서 0xE0 선두 566회, 조회표 2,139회인데 0xE2는 0회 -- 안전하다는 증거가 없다. 능은 코드가 0xE2 0xB6과 0xEA 0x27 둘뿐이라 실제로 걸린다.
- 괄호는 5B가 「, 5A가 」다. 원본 닫는 조각 5A 2F 3B D2 46 1F 이 をお・えた 로 읽혀 」をおぼえた 말고는 맞을 수가 없다. 05_docs/japanese_charmap_manual.csv 는 5A를 へ라 하는데 그건 틀렸다. 그 표는 문맥으로 추정한 171자짜리라 참고만 하고 결론은 그림을 맞춰 낸다.

UI 이전 목록은 이력이지 현재 상태가 아니다 - 2026-08-08

E2는 어디에 있든 글자가 아니다 - 2026-08-08
- 이전 기록의 'E2도 글자 선두다(E2 EB=링, E2 DE=띠)'는 틀렸다. 본문 한가운데의 E2도 명령으로 먹혀 아무것도 안 그려진다. 만능약이 '만 약'으로 나온 것이 증거다.
- 어느 E2가 글자이고 어느 것이 명령인지는 바이트로 못 가른다. E2 B6(능)의 뒤가 0xB6이고 리다이렉트의 뒤는 디스크 번호 0x81~0xD0이라 겹친다. 자리로 가른다.
- 새 글자를 넣을 때 E2 선두는 절대 쓰지 않는다. 실행파일 UI든 대사든 마찬가지다.

폰트는 비트플레인 넷이 한 자리를 나눠 쓴다 - 2026-08-08
- bitmap()은 column, plane = divmod(index % 84, 4) 로 읽고 1 << plane 을 본다. 한 12x12 자리에 글자가 넷 들어 있다.
- 그래서 글자를 옮길 때 니블을 복사하면 안 된다. 이웃 세 글자를 같이 끌고 가서 망친다. 비트 하나씩 옮기고, 옮긴 칸 말고 다른 칸의 bitmap이 그대로인지 전수로 확인한다.
- 조회표(E9/EA)가 같은 font index를 가리킬 수 있으므로, 칸을 덮어쓰기 전에 그 index를 가리키는 조회표 코드가 쓰이고 있는지도 봐야 한다.

대사 본문도 조회표를 쓴다 - 2026-08-08
- 은혜의 혜가 대사 본문에서 EA CC로 적혀 있고 화면에 잘 나온다. 원본 일본어 본문은 E9/EA를 안 썼지만 한글 본문은 쓴다.

선택지는 구조가 아니라 폭에서 깨진다 - 2026-08-08
- 칸 수와 빈 칸만 세면 멀쩡해 보인다. 화면에서 깨지는 것은 줄 폭이다. 한 줄은 228px이고 칸 여럿이 한 줄을 나눠 쓴다. 본문에서 줄이 넘치면 그냥 다음 줄로 접히지만, 메뉴에서 접히면 커서 자리나 다음 칸 위에 얹힌다.
- 폭을 잴 때는 그려지는 대로 재야 한다. E2로 시작하는 칸은 슬롯을 그리고 그 칸의 나머지 바이트는 건너뛴다. 줄바꿈으로만 잘라 세면 204px가 나오는데 게임은 258px를 그린다.
- 원문 폭과 비교하는 것으로는 부족하다. 문제의 줄은 한국어 258px, 일본어 288px여서 비교로는 통과한다. 한글이 그려지는가로 가르는 것도 안 된다 -- 일본어 칸 중에 한글과 그림이 같은 것이 있다. 원판과 바이트가 다른가로 가른다. 안 건드린 일본어 줄은 바이트가 같다.
- E5/E6를 원판 자리에 두는 규칙은 옳다. 그게 커서가 딴 줄에 서던 것을 고쳤다. 대신 원판의 줄 구조가 같이 돌아오므로, 한 줄을 나눠 쓰는 칸들의 문구를 그 폭에 맞춰야 한다.

빈 칸 판정에 그림이 걸린다 - 2026-08-08
- '한글 모양이 아니고 어떤 텍스트 코드도 안 쓴다'로 빈 칸을 고르면 그림 타일이 그대로 걸린다. v146이 그렇게 28곳의 아트워크에 글자 비트를 박아 전투 커서와 바닥 타일을 깨뜨렸다.

v218의 BIOS 뒤 정지는 OT 종료 노드 오인과 FFFF owner 범위 누락이다 - 2026-08-14
- 실패 상태 `HASH-EB6915FE435E3501_1.sav`의 CPU는 PC/EPC `0x80175918`, RA `0x8018F574`, SP `0x801FFF30`이다. CAUSE `0x10000400`은 정상 인터럽트이며 주소 정렬 예외가 아니다.

v219b의 fail-closed 전달 규칙 - 2026-08-14
- 선택기는 기존의 엄격 조건(DMA4, SPRT, 물리 page15/1, font CLUT, 12x12, cache U, A/B V)을 통과한 캐시에만 `marker V=255-U`를 쓴다.
- frame tail은 노드 종류를 미리 가정하지 않고 `DMA words=4`와 raw `U+V=255`를 모두 만족할 때만 표식으로 받는다. 452상태의 OT 310,631노드를 OTHER 포함 전수 검사한 기존 충돌은 0이다.
- owner는 `source_id < 466`일 때만 Huffman 복호화한다. FFFF뿐 아니라 모든 범위 밖 손상값이 fail-closed 된다.

- frame routine에서는 예외 처리 전용 k0/k1을 사용하지 않는다. selector 쪽 기존 사용은 v216과 같으며 v217까지 부팅한 경로다.
- 실제 v218 BIOS 실패 상태 재생은 OTHER 노드 52바이트 보존, FFFF Huffman 진입 0, next active 0을 통과했다. 이 검사는 이후 표식 변경에서 반드시 유지한다.
