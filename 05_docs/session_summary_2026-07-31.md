# 2026-07-31 작업 요약 — P6 확장 글리프 출력 성공

## 한 줄 요약

**P6 확장 글리프 저장소를 실제로 읽어 화면에 출력하는 데 처음으로 성공했다.** v73에 P6 렌더링 경로가 도입된 뒤 16개 빌드 만이다.

---

## 무엇이 문제였나

세 가지 결함이 **동시에** 존재했고, 이전 어느 빌드도 셋을 다 갖춘 적이 없었다.

| 결함 | 증상 | 해결 |
|---|---|---|
| S3032 본문에 `E6 01` 삽입 | 대사 구분자가 깨진 글자로 출력 | v93 |
| 예약 슬롯 소실 → DR_TPAGE가 다음 객체 헤더를 덮어씀 | 아이템명에서 게임 정지 | v95 |
| 고페이지 tpage가 잘못된 텍스처 페이지를 가리킴 | 확장 글리프가 깨진 모양으로 출력 | v97 |

### 왜 오래 걸렸나

v82~v92는 전부 **렌더링 후반부(페이지 선택·분류기)** 만 고쳤다. 실제 결함 중 둘은 그보다 앞이나 옆에 있었다.

```
DAT 원문
  ↓
문자·제어코드 구분        ← E6 문제 (v93에서 해결)
  ↓
글리프 번호 계산
  ↓
U/V 좌표 작성
  ↓
슬롯 할당                ← 오버런 (v95에서 해결)
  ↓
P6 페이지 분류           ← v82~v92가 계속 고치던 지점
  ↓
tpage 좌표               ← 잘못된 페이지 (v97에서 해결)
  ↓
화면 출력
```

## 확인된 구조 (재사용 가능한 사실)

### COMM.IMG는 VRAM 스트립이다

```
458,752 바이트 = 896 바이트 × 512행 = VRAM 448×512 (16bpp) 스트립
왼쪽 끝 = VRAM x4bpp 1280 (텍스처 페이지 5 경계)
state_offset = 0x202058 + (o // 896) * 2048 + (o % 896)
```

COMM 행이 VRAM 행에 1:1 대응한다. 표본 3개에서 오차 0으로 검증했다.

### P6 글리프의 실제 위치

```
x4bpp 2856..3033, y 288..299   (텍스처 페이지 11, 베이스 2816)
2856 − 2816 = 40  ←  글리프 헬퍼의 `addiu a3,a3,40` 과 일치
```

`codex_notes`에 기록돼 있던 `x=1576..1755`는 **절대 좌표가 아니라 스트립 상대 좌표**였다. 1576 + 1280 = 2856. v96이 실패한 원인이다.

### 텍스트 객체 메모리 배치

```
[패킷 배열 limit×52 바이트][68바이트 헤더]
```

세 객체에서 검증했다. 헤더는 정확히 68바이트이고 여유 공간이 없다. 초기화 루틴이 필드 0x00~0x10과 저페이지 tpage 슬롯 두 개(+44, +56)로 0~67을 모두 채운다.

이 배치 때문에 `base + 52*limit`에 쓰는 순간 **다음 객체의 헤더를 정통으로 덮어썼고**, 그게 아이템명 정지의 정체였다.

### 4bpp 비트플레인

한 니블에 독립된 1비트 글리프 4개가 들어있다. 글리프를 확인할 때는 **비트플레인 하나만 분리**해야 한다. 네 개를 OR로 겹쳐 보면 노이즈처럼 보여서 손상으로 오인하기 쉽다.

## 공용 경로 침범 현황

당초 설계 원칙은 "E2 확장 대사만 새 렌더러를 쓰고, 공용 렌더링 코드는 건드리지 않는다"였다. 그러나 v42에서 아이템명·스킬명도 확장 글리프를 쓰게 되면서 전제가 바뀌었다. 현재 목표는 **"실제로 P6에 배치된 글리프만 고페이지로 보내고 나머지는 원본 경로 유지"** 다.

| `0x8016B5D8` 글리프 빌더 | 유지 (row 24 셀에만 `U += 40`) |

## 용어 기준 정립

`05_docs/참고사항/공략본/` 의 스캔 공략본에서 아이템·악세서리·스킬·소환수·능력치·상태이상·인물·지명 표를 추출해 134개 용어를 정리했다.

**공략본은 참고 자료이지 절대 기준이 아니다.** 1990년대 잡지 번역이라 오독이 섞여 있다.

| 분류 | 신뢰도 | 비고 |
|---|---|---|
| 아이템·악세서리 | 높음 | 일본어 병기 대역 |
| 능력치·상태이상·지명 | 높음 | 게임 화면 그대로 |
| 인물명 | 보통 | 비표준 표기 |
| 스킬명 | 낮음 | 한자 음독 위주 |

확인된 오독: `幻のこて`(小手=팔뚝 보호구를 "손끝"으로), `目つぶしの草`(눈을 멀게 함을 "모래"로), `いやしのたてごと`(竪琴=하프를 "거문고"로), `荒獅子太鼓`(太鼓=북을 "태고"로).

**판단 순서**: 원문 정확성 → 고유명사 통일성 → 한국 JRPG 관용.

**글리프 사정은 판단 근거가 아니다.** 모든 최종안을 채택해도 새 글리프 7종이고 여유는 27칸이다.

결정 기록: `05_docs/terminology_decisions.csv` (`02_scripts/build_reference_glossary.py` 로 재생성)

원문이 구분하는데 번역이 뭉뚱그린 곳을 찾아 바로잡았다.

```
果実 / 果物  →  과실
実           →  열매
葉           →  잎
泉           →  샘
```

## 작업 방식에 대한 기록

이번 세션에서 단일 관측으로 내린 결론은 여섯 번 모두 틀렸고, 대조군을 쓴 판단은 모두 맞았다.

| 틀린 결론 | 실제 |
|---|---|
| "E6 01은 줄바꿈이 아니다" | 스크립트 파서에서는 실제 줄바꿈 |
| "GPU 스핀 루프 = 정지" | 정상 상태에도 흔히 나타나는 위치 |
| "스택 폭주" | BIOS 콜백 스택, 정상 프레임 |
| "v92가 정지를 유발" | v91도 정지 → v92 무죄 |
| "25개 코드가 테이블 밖" | 문자열 아닌 곳의 우연한 바이트, 실제 0개 |
| "P6는 x=1576" | 스트립 상대 좌표, 실제 2856 |

맞았던 판단들은 상태저장 101개 SP 분포 비교, UI 문자열 503개 전수 스캔, v70~v98 바이트 대조처럼 **대조군을 둔 경우**였다.

**앞으로 원칙: 대조군 없이 결론을 내리거나 빌드하지 않는다.** v97·v98 빌드 스크립트는 이 원칙에 따라, 좌표와 기하를 아카이브에서 직접 측정하고 불일치하면 빌드를 거부하도록 만들었다.
