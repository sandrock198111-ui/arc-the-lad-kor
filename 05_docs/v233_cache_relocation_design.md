# v233 설계서 — 동적 캐시 자리 이동 (961,480) → (999,420)

## 1. 배경 — 다섯 문장 요약

1. 한글 동적 캐시는 VRAM 사각형 `x961..981, y480..491`(21×12 halfword)에
   글자 픽셀을 올리고, 화면 글자 패킷(SPRT)이 그 자리를 읽는다.
2. 그런데 그 자리는 게임이 월드맵·비행 장면에서 자기 텍스처를 올리는
   자리다. 세이브 467장 합집합에서 252/252 halfword 전부 사용 확인.
3. 그래서 월드맵을 지나면 게임 그림이 글자를 덮고, 캐시는 owners 배열만
   보고 "이미 있다"고 판단해 다시 안 올리므로 깨진 글자가 남는다.
4. 대체 자리는 `x999..1019, y420..431` — 467장에서 0/252, 유일한 후보.
   v222 실기에서 이 자리로 옮기자 그래픽 침범이 사라짐을 확인했다.
5. v222~v229가 전부 실패한 이유는 자리가 아니라 **패킷 읽기 좌표(U·V)
   생성 경로를 잘못 건드렸기 때문**이다. 이제 그 경로가 완전히 밝혀졌으므로
   (아래 3장) 올바른 지점만 바꾼다.

## 2. 이 설계의 핵심 원칙 — v222와 무엇이 다른가

**행 체계(논리 행 40)는 절대 바꾸지 않는다.** 캐시의 색인 계산(base
40×84=3360), 행 판정(문지기 -40), 소스 결정은 전부 "행 40" 전제로 묶여
있고, v197부터 실기로 검증된 경로다. v222/v224는 이걸 35로 바꾸다가
연쇄가 끊겨 실패했다.

v233은 **"논리 행 40 = 물리 자리 (999,420)"**으로 만든다. 즉:
- 색인·행 판정·소스 결정: 그대로 (행 40)
- 픽셀이 실제 앉는 VRAM 자리: (999,420)으로 이동 (업로드 좌표만 변경)
- 패킷이 읽는 U·V: 보정 블록에서 U+156, V−60으로 함께 이동
- 패킷을 식별하는 쪽(classifier/frame): 새 U·V 기준으로 변경

좌표 산수 (텍스처 페이지 15,1 = VRAM x960..1023, y256..511):
```
U = (x_halfword − 960) × 4        x961 → U4,   x999 → U156
V = y − 256                        y480 → V224, y420 → V164
U 이동량 = 156 − 4 = +152 를 기존 +4 보정에 흡수 → 보정을 +4에서 +156으로
V 이동량 = 164 − 224 = −60
lhu/sh 한 쌍으로 U(+0x28)·V(+0x29)를 함께 이동: +156 + (−60<<8) = −15204 = 0xC49C
캐리 없음: U 최대 = 72+156 = 228 < 256
```

## 3. U·V 생성 경로 — 확정 지식 (실측 완료)

패킷 구조: `+0x28 = U`(1바이트), `+0x29 = V`(1바이트). 인접해 있어
`lhu/sh`로 함께 다룰 수 있다(v228·v229 실기에서 동작 확인).

- **V의 원천**: 게임 코드 `0x8016B5A8  sb v0,0x29(a1)` — `V=(row×12)&0xFF`.
  행 40 → 224. 여기는 건드리지 않는다(모든 글자 공용).
- **U의 원천**: 게임 코드 `0x8016B598  sb v0,0x28(a1)` — `U=col×12`.
  여기도 건드리지 않는다.
- **캐시 행 전용 U 보정**: 글리프 패킷 훅 `0x8016B5D8`이 `j 0x8019d074`로
  뛰어드는 블록(v171이 EXE 문자열 풀 영역에 심은 코드). 행 40/63/53/52일
  때만 U에 +4를 더한다. **여기가 v233의 주 편집 지점이다.**
- 행 63/53/52의 정체: EXE 상주 스트립(`plan_bulk_insertion.STRIPS =
  {40:0x801A8800, 63:0x801A8BA8, 53:0x801A93CC, 52:0x801A9774}`).
  이들은 다른 VRAM 자리에 살므로 **U+4를 반드시 유지**해야 한다.
  (v229는 이걸 몰라서 세 행까지 옮겨 손상됐다.)

### 3-1. 보정 블록 현재 원문 (v232 EXE에서 실측, 23명령)

파일 오프셋 = RAM − 0x8011A800. 블록: RAM `0x8019D074..0x8019D0CC`
= 파일 `0x82874..0x828CC`.

```
8019D074  addiu a3,t0,-0x28    ; a3 = row − 40
8019D078  sltiu a3,a3,1        ; a3 = (row==40)
8019D07C  bnez  a3,0x8019D0B4  ; 40이면 보정으로
8019D080  nop
8019D084  addiu a3,t0,-0x3f    ; row − 63
8019D088  sltiu a3,a3,1
8019D08C  bnez  a3,0x8019D0B4
8019D090  nop
8019D094  addiu a3,t0,-0x35    ; row − 53
8019D098  sltiu a3,a3,1
8019D09C  bnez  a3,0x8019D0B4
8019D0A0  nop
8019D0A4  addiu a3,t0,-0x34    ; row − 52
8019D0A8  sltiu a3,a3,1
8019D0AC  beqz  a3,0x8019D0C4  ; 넷 다 아니면 건너뜀
8019D0B0  nop
8019D0B4  lbu   a3,0x28(a1)    ; ── 공통 보정 (U += 4)
8019D0B8  nop
8019D0BC  addiu a3,a3,4
8019D0C0  sb    a3,0x28(a1)
8019D0C4  lbu   v0,0xe(a2)     ; ── 마무리 (가로챈 원본 명령 복원)
8019D0C8  j     0x8016b5e0     ; 게임 코드로 복귀
8019D0CC  nop                  ; j 의 delay slot — 반드시 보존
```

레지스터 계약: 진입 시 `t0=row`, `a1=패킷 주소`, `a2`는 게임 상태(마무리
`lbu v0,0xe(a2)`가 사용). `a3`은 자유롭게 써도 된다.

### 3-2. 새 블록 (같은 23슬롯 안, 행 40만 분리)

MIPS 규칙: 분기 직후 1명령(delay slot)은 분기 성패와 무관하게 실행된다.
이를 이용해 sltiu를 없애고 delay slot에 다음 검사의 addiu를 넣는다.
분기 조건은 이미 평가된 뒤라 delay slot에서 a3를 덮어도 안전하고,
분기가 성립해 날아간 곳(ROW40/COMMON)은 a3를 다시 읽으므로 무해하다.

```
8019D074  addiu a3,t0,-0x28    ; row − 40
8019D078  beqz  a3,ROW40       ; 40 → 전용 보정
8019D07C  addiu a3,t0,-0x3f    ; (delay) row − 63
8019D080  beqz  a3,COMMON      ; 63 → 스트립 공통 보정
8019D084  addiu a3,t0,-0x35    ; (delay) row − 53
8019D088  beqz  a3,COMMON
8019D08C  addiu a3,t0,-0x34    ; (delay) row − 52
8019D090  bnez  a3,FIN         ; 넷 다 아니면 보정 없이 마무리
8019D094  nop                  ; (delay)
COMMON:                        ; ── 행 63/53/52: 기존과 동일 U += 4
8019D098  lbu   a3,0x28(a1)
8019D09C  nop                  ; load delay
8019D0A0  addiu a3,a3,4
8019D0A4  sb    a3,0x28(a1)
8019D0A8  beq   zero,zero,FIN  ; 무조건 분기 (b FIN)
8019D0AC  nop                  ; (delay)
ROW40:                         ; ── 행 40(캐시): U += 156, V −= 60
8019D0B0  lhu   a3,0x28(a1)    ; U | V<<8
8019D0B4  nop                  ; load delay
8019D0B8  addiu a3,a3,-15204   ; 0xC49C = +156 | (−60)<<8
8019D0BC  sh    a3,0x28(a1)
FIN:                           ; ROW40에서 자연 낙하
8019D0C0  lbu   v0,0xe(a2)     ; 마무리 (원본 명령)
8019D0C4  j     0x8016b5e0
8019D0C8  nop                  ; delay slot
8019D0CC  nop                  ; 여분 1슬롯
```

23슬롯 중 22개 사용, 마지막 1개는 nop. 블록 밖은 1바이트도 안 바뀐다.
`0x8019D0D0` 이후는 건드리지 않는다.

## 4. 전체 편집 지점 — 정확히 8곳

편집 도구: `build_arc1_v222_claude_cache_row35_x999.py`의 `unique()` 방식
(고유 워드 검색 + 사전값 확인)을 그대로 재사용한다. 주소를 하드코딩하지
말고 기존 빌더의 탐색 로직을 쓸 것 — v190 상주는 생성 코드라 판마다
오프셋이 다를 수 있다.

| # | 이름 | 위치 | 기존 → 신규 | 이유 |
|---|---|---|---|---|
| 1 | 보정 블록 재배치 | RAM 0x8019D074..CC (23워드) | 3-1 → 3-2 | 행 40만 U+156·V−60, 스트립 행은 U+4 유지 |
| 2 | classifier V | `addiu v0,v0,-224` (LOW_CLASSIFIER 안) | −224 → −164 | 패킷 V로 캐시를 식별하는 곳 |
| 3 | frame V | `addiu t5,t5,-224` (상주 frame 안) | −224 → −164 | frame의 캐시 패킷 판정 |
| 4 | frame U | `addiu t6,t6,-4` (상주 frame 안, follow=`sltiu t5,t6,84`) | −4 → −156 | 패킷 U에서 슬롯 역산 `(U−보정)/12` |
| 5 | cache X | `addiu t0,t0,961` (상주 이미지 안) | 961 → 999 | LoadImage 목적지 X |
| 6 | upload_rect | 상주 데이터 `(961,480,3,12)` | (999,420,3,12) | LoadImage 사각형 (셀 단위 갱신이라 폭 3) |
| 7 | virtual row 문지기 | `addiu t0,a3,-40` (low helper) | **불변** | v222 실패 원인 — 절대 바꾸지 말 것 |
