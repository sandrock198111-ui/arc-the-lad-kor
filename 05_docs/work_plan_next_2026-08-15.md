**목표**: 사용자의 V234 콜드부팅 세이브로 성공/실패를 판정하고 다음

**전제**: 사용자가 세이브를 첨부한다. v234는 EXE가 v233과 1워드 달라
DuckStation 해시가 새로 나온다(해시로 판별 가능). 그래도 mtime을
`03_output/V234.bin` 생성 시각과 대조해 이중 확인하라.

**성공 기준** (모두 충족):
- 비행/월드맵 장면 **중에** 지명 글자가 유지된다
- 월드맵 이탈 직후 대사가 **즉시** 정상이다 (v233의 느린 회복 소멸)
- 글자 깜빡임이 없거나 사용자가 체감 못 하는 수준
- 전투·메뉴·일반 대사는 v233과 동일

**분석 절차** (스크립트는 전부 `02_scripts/`):

  다음 수: "장면 전환 감지 후 1회 재업로드" 설계(새 작업 — LoadImage

- 그 외 증상 → `v233_cache_relocation_design.md` 7장 진단 트리

# 전 작업 공통 규칙 (이 세션에서 비싸게 배운 것)

1. **점유 지도는 0 쓰기를 못 본다.** "빈 자리"는 존재하지 않는 개념.
   자리 결정은 항상 재업로드/fail-closed 같은 회복 수단과 함께
2. **글리프 원천은 현행 체인의 검증 산출물에서만** (v190 Huffman).
   색인은 시점 의존이다
3. **행 체계 40 불변**: 문지기 -40, index base 40*84는 어떤 패치에서도
   건드리지 않는다
4. **행 63/53/52는 EXE 스트립**: U+4 유지 필수
5. **참조 집계는 1바이트 토큰 포함**
6. **package_patch_to_cue.py 사용 금지** (SYSTEM.CNF 추가로 LBA가 밀림).
   `package_test_iso.py` + `verify_iso_layout.py` PASS 확인만 사용
7. **EXE가 같으면 DuckStation 해시도 같다**: 세이브 판별은 mtime+내용
8. **정적 검증 통과 ≠ 실기 통과**: R3000 실행 모형(분기·로드 지연 구현)
   까지 돌리고도 실기 실패한 사례가 4번 있다. bible 승격은 실기 관찰 후
9. 검증 게이트 4종은 모든 빌드에서: release_readiness, resident_routines,
   (texture_canaries — v194 기준 하드코딩이므로 빌더 내장 diff 가드로
   대체 가능), verify_iso_layout
10. 커밋 규칙은 AGENTS.md대로: 00_original/03_output/99_backup/ex/
    06_tools 커밋 금지, 문서·스크립트·분석 CSV만
