아크더래드1 PS1 일본판 한글화 인수인계 바이블 v15
- 바이너리/구조/시행착오/다음방 지시문 통합판 -

작성 목적
- 이 문서는 단순 요약이 아니라, 지금까지의 구조 파악, 바이너리 단서, 실패한 방식, 성공한 방식, 금지사항을 최대한 포함한 인수인계용 문서다.
- 새 대화방/다른 AI/다른 작업자/아크더래드2 같은 구조 유사 게임 분석자가 이 문서만 보고도 같은 시행착오를 반복하지 않게 하는 것이 목적이다.
- 단, 아래 수치 중 일부는 “실험으로 관찰된 값”이며, 완전한 엔진 사양서가 아니다. 확정/추정/실패 사례를 반드시 구분해서 읽어야 한다.

============================================================
0. 최종 현재 결론
============================================================

1) 일본판 기준 한글 출력 자체는 성공했다.
- COMM.IMG의 공용 CJK 폰트 슬롯을 바꾸면 대사창/이름창/메뉴/UI 글자가 실제로 바뀐다.
- 일본판은 대략 12x12 고정폭 CJK 출력 구조라 영어판보다 한글에 훨씬 유리하다.
- “촌장 / 여기까지요 / 혼자 가시오” 출력은 성공했다.

2) 가장 안정적인 현재 방식은 다음과 같다.
- 기존 DAT 블록 길이 안에서 한글을 넣는다.
- 긴 문장은 단축/의역한다.
- 남는 공간은 0x00으로 자르지 말고 safe filler로 채운다.
- safe filler는 0x04 계열을 사용하되, 실제 출력되는 slot 0을 COMM.IMG에서 빈칸으로 만든다.

3) 지금 단계의 벽은 세 가지다.
- 장면-대사 매칭: DAT 블록 순서대로 번역문을 밀어 넣으면 장면과 대사가 어긋난다.
- 폰트 품질: 12x12 안에서 읽히는 전용 1비트 도트 한글이 필요하다.
- UI/메뉴/전투: COMM.IMG만 바꾸면 안 되고, UI 원문 문자열 위치를 직접 찾아 패치해야 한다.

4) 전체 DAT를 무차별 패치하면 안 된다.
- “대사처럼 보이는 후보”를 모두 바꾸면 초상화/얼굴/캐릭터/이벤트 제어값까지 건드려 얼굴 밀림, UI 깨짐, 진행 꼬임이 생긴다.
- full compact v1 방식은 실패로 기록한다.

5) DuckStation 세이브스테이트로 검수하면 안 된다.
- 새 패치 적용 후에는 반드시 게임 재부팅 → 메모리카드 세이브 로드로 확인한다.

1. 일본판 파일 구조
============================================================

관찰된 추출 구조 예시:

PSX.EXE
COMM.DAT
COMM.IMG
COMM.SND
S000.DAT
S000.IMG
1/S1011.DAT
1/S1011.IMG
1/S1071.DAT
1/S1071.IMG
...
21/S2011.DAT
21/S2012.DAT
...

현재까지 확인/추정된 역할:

COMM.IMG
- 공용 폰트/공용 UI 그래픽 성격.
- 대사창, 이름창, 세이브창, 전투 UI, 기술명, 하단 도움말 등이 같은 공용 글리프 슬롯을 참조한다.
- COMM.IMG를 잘못 바꾸면 대사뿐 아니라 UI/숫자/아이콘/기술명까지 같이 깨진다.

COMM.DAT / PSX.EXE
- UI/메뉴/세이브/전투 문자열 원문 위치가 여기에 있을 가능성이 있다.
- 아직 직접 문자열 패치 단계는 완전히 끝나지 않았다.
- UI는 COMM.IMG 폰트 교체만으로 번역하면 안 되고, 원문 문자열 위치를 찾아 직접 바꿔야 한다.

1/S1071.DAT
- 초반 신전 입구 첫 대화에 연결된 것으로 확정.
- 시장/촌장 첫 대사, 쿠쿠루 반응 등 초반 입구 대사 일부 포함.

1/S1011.DAT
- 산 진입/산 정상/하산 후 신전/아크 집 초반 흐름에 연결된 것으로 확인.
- 한 파일 안에 여러 장면이 섞여 있어 DAT 내부 순서만으로 번역문을 넣으면 장면이 어긋날 수 있다.

1/S1072.DAT
- 산/신전 이후 전환 구간 일부에 연결된 것으로 확인.

1/S1021.DAT
- 아크 집 안 장면 일부에 연결된 것으로 확인.

21/S2011.DAT, 21/S2012.DAT 등
- 첫 전투 이후 구간 후보.
- 넓게 패치했을 때 초상화/얼굴 밀림이 발생한 적 있음.
- 반드시 한 파일/한 장면 단위로 좁게 검증해야 한다.

2. 폰트/GPU/COMM.IMG 관련 바이너리 단서
============================================================

2-1. GPU 패킷 관찰값

대사/폰트 쪽에서 관찰된 GPU 패킷 예시:

65000000
004E00CA
7FC2009C
000C000C

해석:
- 000C000C는 글자 출력 크기 12x12와 관련 있어 보인다.
- 일본판은 CJK용 12x12 고정폭에 가까운 구조로 판단한다.
- 이 값 자체를 무작정 바꾸지는 않았다. 현재는 구조 확인용 단서로만 기록한다.

대사창 쪽 GPU 명령으로 관찰된 값:

E1000005

대사창 사각형/배경 관련으로 보였던 값:

2B000000
001C0026
001C011A
00620026
0062011A

주의:
- 위 값들은 GPU/창/사각형 관련 관찰값으로 보이나, 아직 수정 대상이 아니다.
- 폰트/대사 패치에는 직접 사용하지 않았다.

2-2. COMM.IMG 위치 계산 추정식

이전에 추정한 매핑:

VRAM font raw 위치 = y * 0x80 + x
COMM.IMG 위치     = 0x000004 + y * 0x380 + x

의미:
- COMM.IMG 앞쪽 영역이 공용 폰트/공용 그래픽으로 강하게 의심된다.
- COMM.IMG 끝쪽이 아니라 앞쪽부터 실제 글리프/공용 UI 리소스가 존재할 가능성이 크다.
- 이 식은 관찰 기반 추정식이다. 다른 장면/다른 파일에서 반드시 재검증해야 한다.

2-3. 폰트 처리 결론

실패한 방식:
- 나눔고딕/굴림/도움/노토 등을 단순히 12x12로 축소.
- 회색 안티앨리어싱 포함.
- 결과: 회색 픽셀이 게임 팔레트에서 흰색처럼 떠서 글자가 굵고 뭉개짐.

성공 방향:
- 12x12 전용 1비트 도트 한글.
- 회색/그라데이션/안티앨리어싱 제거.
- 흰색 1픽셀 획 중심.
- 받침 있는 글자는 과감하게 단순화.
- UI용 글자는 일반 대사용보다 더 높은 품질의 수동 보정 필요.

주의:
- 자동 조합식 한글은 빠르게 글자를 늘릴 수 있으나, 난독 글자가 생긴다.
- 실제 배포용은 자동 생성 + 난독 음절 수동 보정이 필요하다.

3. 확인된 대사 DAT 패턴과 오프셋
============================================================

3-1. 일반 대사 명령 후보 패턴

관찰된 일반 대사 후보 패턴:

29 00 00 00 7F 00 ... text ... 00 00

의미:
- 초반 S1071/S1011 등에서 대사 블록 후보를 잡는 데 사용했다.
- 하지만 이 패턴이 모든 대사/텍스트를 잡는 것은 아니다.
- 자동 진행 대사, 장소명, 메뉴, UI, 전투 도움말, 기술명은 다른 구조일 수 있다.

절대 금지:
- 이 패턴으로 잡히는 후보 전체를 무조건 패치하지 말 것.
- 일부 후보는 대사가 아니라 이벤트/초상화/캐릭터/제어 데이터일 수 있다.

3-2. S1071.DAT 확정/관찰 오프셋

1/S1071.DAT는 초반 신전 입구 첫 장면 대사 파일로 확정.

초기 위치 확인 과정:
- S1011.DAT 0x478AA에서 38 → 26 변경 테스트는 현재 화면 이름칸 변화가 없어 실패/비확정으로 기록.
- 이후 S1071.DAT 쪽을 건드렸을 때 이름칸이 村長에서 이상하게 바뀌어 S1071이 현재 장면임을 확인.

본문 첫 글자 확인:
- 일본어 첫 본문 “さあ...”의 さ를 あ로 바꾸는 테스트 성공.
- 당시 후보:
  본문 시작 위치 = S1071.DAT 0x478DC 근처
  0x3A = さ 로 추정
  0x3F = あ 로 추정
- 이것은 해당 본문 위치가 실제 대사 바이트임을 검증하는 데 사용.

S1071 초반 블록 관찰값:

0x478D6-0x478FD : 시장/촌장 첫 대사
0x47932-0x4795B : 얼굴 나오는 첫 반응 대사
0x4798E-0x479C5 : 시장/촌장 두 번째 대사
0x479FA-0x47A00 : 짧은 얼굴 반응 대사

본문 시작 후보:
0x478DC 근처

줄바꿈 제어 관찰:
E6 01

주의:
- 오프셋은 현재 사용한 추출본 기준이다.
- 같은 게임이라도 파일 추출/패킹 방식이 다르면 오프셋이 달라질 수 있다.

3-3. S1011.DAT 관련

1/S1011.DAT는 산 진입/산 정상/하산 후/집 안 일부에 연결.
S1011 내 대사 블록은 총 9개로 잡힌 적이 있다.
S1011-09 short 같은 매우 짧은 블록도 확인.

주의:
- S1011은 여러 장면을 포함하는 이벤트 스크립트 성격이다.
- “파일 하나 = 장면 하나”가 아니다.
- DAT 내부 순서와 실제 플레이 순서를 동일하다고 가정하면 안 된다.

3-4. 대사 후보 스캔 수치

과거 스캐너 결과로 기록된 수치:
- 전체 대사 후보: 약 2641개
- 비어 있지 않은 후보: 약 2354개
- 1번 폴더 후보: 약 132~133개

주의:
- 이 숫자는 “대사일 가능성이 있는 후보” 수치이지, 확정 대사 수가 아니다.
- full compact v1에서 이 후보들을 넓게 건드렸다가 얼굴 밀림/초상화 오류가 발생했다.
- 따라서 스캐너 결과는 원문-장면 매칭 전의 후보 목록으로만 사용해야 한다.

============================================================
4. 문자 코드/한글 인코딩 관련
============================================================

4-1. Shift-JIS 검색 실패

일본어 대사는 Shift-JIS 원문 문자열로 단순 검색되지 않았다.
가능성:
1) 게임 전용 문자 코드 사용
2) 1바이트 가나 + 2바이트 한자/특수 코드 혼합
3) 이벤트 명령/인덱스/압축 구조 안에 텍스트 포함

4-2. 글자 교체 검증

성공한 검증:
- 村長 슬롯을 한글 “촌장” 글리프로 바꾸면 이름칸에 한글 표시 가능.
- 본문 さ → あ 바이트 변경으로 화면 실제 변경 확인.
- 따라서 DAT 코드와 COMM.IMG 글리프 슬롯이 연결됨.

주의 코드 추정:
- 村 = DD 0B, 長 = D4 25 처럼 보인 추정이 있었으나 확정 코드표로 쓰면 안 된다.
- 실제로는 1바이트/2바이트/제어코드가 섞여 있어 화면 반응 기준으로 검증해야 한다.

4-3. 한글 인코더 방향

초기 방식:
- “여기까지요” 같은 문장 전체를 정해진 바이트열로 넣음.

개선 방식:
- 여/기/까/지/요/혼/자/가/시/오/촌/장 등 글자 단위 인코더 도입.
- 문장을 글자 단위로 조립.

문제:
- 자동 슬롯 배정이 기존 일본어/UI/숫자 슬롯과 충돌하면 UI나 대사가 깨진다.
- 낮은 슬롯을 함부로 쓰지 말 것.

============================================================
5. 패딩/남는 공간 처리 - 매우 중요
============================================================

대사 번역이 원래 일본어 블록보다 짧을 때 남는 공간 처리에서 큰 시행착오가 있었다.
반드시 아래 원칙을 지킨다.

실패 1: 0x20 패딩
- 남는 공간을 0x20으로 채움.
- 결과: 뒤에 かかか... 같은 글자가 출력됨.
- 결론: 0x20은 이 게임에서 안전 공백이 아니다.

실패 2: 0x86 패딩
- 남는 공간을 0x86으로 채움.
- 결과: 뒤에 ㅅㅅㅅ... 같은 글자가 출력됨.
- 결론: 0x86도 안전 공백이 아니다.

실패 3: 0x00 패딩/종료
- 남는 공간을 0x00으로 채움.
- 결과: 남는 글자는 사라졌으나 스크립트가 꼬이고 이상한 장면 진입/무한 반복 발생.
- 0x00은 단순 공백이 아니라 텍스트 종료/스크립트 경계로 작동할 수 있다.
- 문장 중간 띄어쓰기에 0x00을 넣어도 대사가 끊길 위험이 있다.

성공: safe filler 방식
- 기존 블록 길이는 유지한다.
- 남는 공간은 0x00으로 자르지 않는다.
- filler byte로 0x04를 사용했다.
- 그러나 처음에는 ####가 출력됨.
- 확인 결과 실제 출력되는 슬롯이 slot 0로 판단되어 COMM.IMG의 slot 0을 빈칸으로 만들자 해결.

현재 원칙:
- 남는 공간은 0x00으로 종결하지 말 것.
- 기존 블록 길이를 유지할 것.
- safe filler + blank slot 0 조합 사용.
- 이 방식에서는 무한 반복/이상 장면 진입이 사라졌다.

============================================================
6. 실패한 패치 방식 기록
============================================================

6-1. 진단팩/마커팩 장기 사용 실패

가가가/요요요/파일별 마커 방식은 파일 확인에는 유용했지만, COMM.IMG까지 바꾸면 원문 일본어와 한글이 섞여 보여 판단이 흐려진다.
마커팩은 진단용으로만 잠깐 사용하고, 진행용 패치와 분리해야 한다.

6-2. full compact v1 실패

목표:
- 전체 대사 후보 DAT 153개, 후보 블록 2351개에 단축/의역을 넣으려 함.

결과:
- 초상화/얼굴이 밀리는 오류 발생.
- 대사처럼 보인 후보 중 일부가 실제로는 초상화/이벤트/제어값이었다.

결론:
- 전체 후보 무차별 패치 금지.
- 파일/장면/블록을 좁혀서 검증해야 한다.

복구:
- COMM.IMG 폰트는 유지.
- full compact v1이 건드린 전체 DAT는 원본으로 복구.
- 초반 1번 폴더의 확인된 안정 패치만 유지.

6-3. 장면-대사 매칭 실패

문제:
- DAT 블록 순서대로 번역 원고를 밀어 넣으면 신전 장면에 집 장면 대사가 나오거나, 집 장면에 다른 대사가 나오는 문제가 발생.

원인:
- DAT 내부 순서와 실제 게임 장면 순서가 1:1이 아니다.
- 같은 파일에 여러 장면/분기/자동 진행/미사용 대사가 섞여 있다.

해결 방향:
- “파일/블록 → 실제 장면 → 원문 → 번역문” 1:1 매칭 후 패치.
- 매칭 안 된 블록은 건드리지 않는다.

============================================================
7. UI/메뉴/전투 관련 바이너리 단서
============================================================

7-1. UI는 COMM.IMG만으로 번역하면 안 된다

확인된 UI 대상:
- セーブしますか？ / はい / いいえ
- バーングラウンド
- 전투 커맨드 선택창
- 기술명/마법명 팝업
- 전투 하단 도움말
- HP/MP/숫자/기호

결론:
- 이들 모두 COMM.IMG 공용 글리프를 사용한다.
- 그러나 COMM.IMG만 바꿔 일본어 슬롯을 한글로 덮으면 다른 UI가 같이 깨진다.
- 따라서 UI는 반드시 원문 문자열 위치를 찾아 바이트를 직접 한글 코드로 교체해야 한다.

잘못된 방식:
COMM.IMG의 일본어 글자 슬롯을 한글로 덮어쓰기

맞는 방식:
1) UI 원문 문자열 위치 찾기
2) UI 문자열 자체를 한글 코드로 교체
3) COMM.IMG에는 해당 한글 글리프만 안전 슬롯에 배치
4) 숫자/기호/아이콘/HP/MP 슬롯은 보호

7-2. UI locator에서 관찰된 코드 화면

UI locator 패치에서 화면에 숫자 코드가 출력되어 각 UI가 공용 폰트 슬롯을 쓰는 것을 확인했다.
아래 값은 화면상 관찰된 코드 표기이며, 원문 문자열/슬롯 매핑 연구용 단서다.

세이브 메뉴 비슷한 화면에서 관찰:
04 4E 0C 32 0E 0C 08 06 09 16 08
반복 라인 유사값 관찰.
짧은 선택지 쪽:
09 12 14 07 0C
하단 쪽:
20 0C 18 0B 11 0C 0B 0B 0F 0A 0E 0B

지도/세이브 선택창 관찰:
00 00 4E 0C 32 07 09 04 07 0E 00 00
선택지:
09 06 00 00 06 06 11

전투/기술명/하단 도움말 관찰:
00 C0 31 08 0A 00 06 11 09 04 07 0E 00
선택지:
09 06 00 00 06 06 11

기술명/커맨드 팝업 관찰:
2B 0C 0C 1F 15 1C 0C 25

전투 하단 도움말 관찰:
08 27 5C 08  [버튼 아이콘]  08 4A 35 0C 4E 14 07 09 0A

또 다른 팝업 관찰:
06 A9 40 06 21 2E 1A 1E

주의:
- 위 값들은 locator 화면에서 보인 값으로, 아직 완전한 문자열 매핑표가 아니다.
- 하지만 UI가 공용 폰트 슬롯을 쓰고 있음을 확인한 중요한 단서다.

7-3. UI 다음 작업 우선순위

1차 UI 직접 패치 대상:
- 예

8. 번역/길이 제한 관련 현실적 판단
============================================================

현재 안정 방식은 기존 일본어 대사 블록 길이 안에 한글을 넣는 방식이다.
따라서 긴 한국어 문장은 원고 그대로 넣기 어렵다.

예:
원고:
우리는 여기까지일세.. 앞으로의 길은 그대 혼자 가야 될 것이야.

현재 안전 방식:
여기까지일세
이 뒤는 혼자 가게

즉, 단축/의역은 필수다.

긴 문장을 원문 그대로 넣으려면:
1) DAT 내부 빈 공간으로 텍스트 이전
2) 포인터 수정
3) 파일 크기/로드 주소/섹터 구조 분석
4) ISO 재패킹 안정화
이 필요하다.

이것은 전문 패치팀도 벽이라고 말하는 영역이며, 단순 한글패치가 아니라 스크립트 엔진/롬해킹 수준이다.

현실적 추천:
- 먼저 기존 블록 안에서 의미가 통하는 압축 번역으로 플레이 가능한 초벌 패치 제작.
- 이후 꼭 필요한 핵심 대사만 포인터 확장 연구.
