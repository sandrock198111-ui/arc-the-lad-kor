# 16px 조합형 전환 — 사전 조사

2026-08-16. 폰트 후보를 받기 전에 확정할 수 있는 것들을 모아 둔다.
수치는 전부 실측이며, 근거가 없는 항목은 "미확정"으로 적었다.

---

## 왜 전환을 검토하는가

v197부터 v237까지 열두 판을 만들며 동적 캐시의 자리 문제를 풀려 했고,
2026-08-16 기준 모든 경로가 막혔다(`v236_promotion_plan_2026-08-16.md` 참조).
근본 원인은 하나다 — **완성형은 글자마다 칸이 필요한데 VRAM에 그만한 자리가
없다.** 조합형은 그 전제를 없앤다.

---

## 1. VRAM 예산 — 전환의 가장 큰 근거

```
현재  완성형 12x12   아틀라스 42행 x 21열 = 882칸 (x4면 = 3528자)
                     VRAM 31,752 halfword = 62 KB

조합형 16x16 조각 128개    8,192 halfword = 16 KB   (현재의 25%)
조합형 16x16 조각 256개   16,384 halfword = 32 KB   (현재의 51%)
조합형 14x14 조각 128개    5,376 halfword = 10.5 KB (현재의 16%)
```

텍스처 페이지 하나가 32 KB이므로 **16x16 조각 128개는 페이지 하나에 정확히
들어간다.** 조각을 256개로 늘려 품질을 올려도 지금의 절반이다.

그리고 다음이 전부 불필요해진다.

```
동적 캐시 코드   decoder 568B + huffman 232B + frame 584B = 1,384B
캐시 데이터      owners / active_mask / next_slot / upload_rect
범위표           0x801A74C0
조회표           0x801A7520 대역
정적 승격 체계   v231 / v232 / v236
```

상주 블록 5,356B가 거의 통째로 비므로, 조합 로직을 넣을 코드 공간 문제도
동시에 해결된다. **32바이트가 없어서 막혔던 상황이 뒤집힌다.**

---

## 2. 크기 선택 — 16px

줄 수 영향을 대사 8,448개로 실측했다(한 줄 228px 기준).

```
              1줄     2줄     3줄     4줄    4줄초과   5줄초과
12px(현재)   63.1%   21.4%   11.1%   3.4%     88개     63개
14px         60.9%   19.4%   12.9%   4.7%    171개     79개
16px         58.4%   18.2%   14.3%   6.4%    232개    108개
```

**16px의 추가 부담은 144개 대사**다(232 - 88). 14px을 골라도 83개는 손봐야
하므로 실질 차이는 61개뿐이다.

코드 난이도는 오히려 16px이 낮다.

```
x12   sll 1 ; addu ; sll 2      현재
x14   sll 3 ; subu ; sll 1      같은 3명령
x16   sll 4                     1명령
```

품질은 굴림체로 12px과 16px을 렌더해 비교했다. 12px에서는 `괜`의 ㅙ가 붙고
`찮`의 받침이 뭉치며 `데`/`더` 구분이 어렵다. 16px에서는 획마다 여백이 남는다.
**완성형 12px이 그 정도이므로 조합형 12px은 그보다 나쁘다** — 참고 배포본
(ex 폴더)이 12px를 유지한 것을 확인했고, 그 결과가 사용자가 말한 "모양이
구리다"에 해당한다.

## 3. 렌더러 변경 지점 25곳

`0x8016B000~0x8016C400` 대역을 전수 조사했다. 단순 치환이 아니며 역할별로
처리가 다르다.

### A. 좌표 x12 계산 — 7곳

```
0x8016B564  sll v0, a1, 1     0x8016B58C  sll v0, v1, 1   (U = 칸 x 12)
0x8016B59C  sll v0, t0, 1     (V = 행 x 12)
0x8016B690  sll s0, a1, 1     0x8016B848  sll a1, v1, 1
0x8016BE9C  sll v0, a2, 1     0x8016C328  sll v0, v1, 1
```

각각 `sll 1 ; addu ; sll 2` 3명령이다. `sll 4` 한 명령으로 바꾸고 남는 두
자리는 nop. **명령 수가 줄어드는 방향이라 안전하다.**

### B. 패킷 폭/높이 저장 — 11곳

```
0x8016B46C / 0x8016B488 / 0x8016B5EC / 0x8016B5F8 / 0x8016B6F4 / 0x8016B708
0x8016BEC8 / 0x8016BECC / 0x8016BFF4 / 0x8016C048 / 0x8016C078
```

`sh ?, 0x2c(?)` = 폭, `sh ?, 0x2e(?)` = 높이. **저장값의 출처를 각각
따라가야 한다** — 상수 12인 곳과 변수인 곳이 섞여 있다. 미확정 항목이다.

### C. 12 상수 직접 사용 — 5곳

```
0x8016B160  ori v0, zero, 12   -> sb v0, 0xd(s1) ; sb v0, 0xe(s1)
0x8016B348  ori a1, zero, 12   -> jal 0x8016B4B0   (함수 인자)
0x8016B394  ori a0, zero, 12   -+
0x8016B398  ori a1, zero, 12   -+ 같은 호출의 두 인자
0x8016B6E0  ori v0, zero, 12   -> sb v0, 0x2b(s0)
```

### D. 루프 한계 — 2곳 (주의)

```
0x8016B198  addiu s0, s0, 12  ->  slti v0, s0, 0x44  ->  bnez (루프)
0x8016C2D4  addiu a0, s0, 12
```

**`0x44`(68)은 12에 연동된 한계값이다.** 12씩 증가하며 68 미만까지 도는
루프이므로 16으로 바꾸면 한계도 함께 조정해야 한다. 이런 연관 상수를
놓치면 루프가 한 칸 덜 돌거나 넘친다. **B와 D가 이 작업의 실제 위험
지점이다.**

## 4. 착수 순서

### 1단계 — 크기만 먼저 (폰트 없이 가능)

완성형 글꼴을 그대로 두고 렌더러만 12 -> 16으로 바꾼다. 글자는 16칸 안에
작게 그려지지만 **레이아웃이 따라오는지**를 실기에서 검증할 수 있다.
줄 간격, 커서 위치, 대사창 넘침, 선택지 정렬이 확인 대상이다.

여기서 실패하면 조각을 아무리 잘 그려도 소용없으므로 위험을 앞에서
걷어내는 순서다.

### 2단계 — 조각 글꼴

자유 라이선스 픽셀 폰트에서 16px 비트맵을 추출하거나 직접 그린다.
후보는 사용자가 조사 중이다. **굴림/돋움 계열은 배포 라이선스 문제로
쓸 수 없다** — 비교용 렌더에만 사용했다.

조각 수는 128개(8x4x4)가 기본이고, VRAM 여유가 있으므로 256개까지
올려 품질을 높일 수 있다.

### 3단계 — 조합 렌더 로직

한 글자를 초성/중성/종성 스프라이트 3개로 그린다. 캐시가 사라지며 비는
상주 1,384B에 들어간다.

### 4단계 — 대본 재인코딩

완성형 코드 -> 조합형 코드. 기존 삽입 파이프라인(v190~v210 체인)을
재사용할 수 있다. 2바이트 코드 폭을 유지하면 포인터가 불변이다.

### 5단계 — 줄 넘침 손질

16px에서 4줄을 넘는 232개 중 현재도 넘는 88개를 뺀 **144개**가 대상이다.

## 7. 글꼴 확보 완료 (2026-08-16 저녁)

`iolo/8x4x4-fonts` 저장소에서 조건에 맞는 글꼴을 확보했다. 위 5절까지의
"미확정" 항목이 전부 실물로 해소됐다.

### 확보한 것

```
출처       github.com/iolo/8x4x4-fonts   (MIT / OFL-1.1)
선택       Hanme_8x4x4.bdf               (12종 중 하나, 나중에 교체 가능)
형식       BDF — 텍스트 기반 비트맵. TTF 렌더 없이 픽셀을 직접 읽는다
크기       16x16
조각       360개 (0xF600~0xF767 연속),  그중 비어있지 않은 것 344개
```

### 조각 배치 — 실측으로 확정

```
idx   0..159   초성  20개(빈칸+19자모) x 8벌 = 160
idx 160..247   중성  22개(빈칸+21자모) x 4벌 =  88
idx 248..359   종성  28개(빈칸+27자모) x 4벌 = 112
                                        합계   360
```

비어있지 않은 344개 = 19x8 + 21x4 + 27x4 로 정확히 일치한다.

### 조합 규칙 — 검증 완료

표준 8벌식이 그대로 맞았다. 중성 그룹으로 초성 벌을, 초성 종류로 중성 벌을,
중성 그룹으로 종성 벌을 고른다.

```
중성 그룹   A = ㅏㅐㅑㅒㅓㅔㅕㅖㅣ    B = ㅗㅛㅡ    C = ㅜㅠ    D = 복합
초성 벌     그룹(A=0,B=1,C=2,D=3) + (받침 있으면 +4)
중성 벌     (초성이 ㄱ/ㅋ이면 1, 아니면 0) + (받침 있으면 +2)
종성 벌     중성 그룹 (A=0,B=1,C=2,D=3)
```

`괜 찾 아 있 다 그 런 데 말 했 잖 군`을 조립해 전부 정상 렌더를 확인했다.
ㅙ, ㄶ, ㅆ, ㅜ 같은 복합 자모와 겹받침이 모두 제대로 조립된다.
