# v236~v237 계획 — 138자 승격으로 회복 코드 공간을 만든다

2026-08-16. v235 실기 결과에서 도출한 실행 계획. 수치는 전부 실측이다.

## 배경

v235로 캐시 자리 이동은 완성됐다(월드맵 지명 정상 출력, owners 중복 0).
남은 결함은 **월드맵 이후 회복 불가** 하나다. 비행 중 우리 칸 21개 중
12개가 0으로 지워지는데, 캐시가 `owners` 장부만 보고 존재를 판정하므로
재업로드가 일어나지 않는다.

자리로는 더 피할 수 없다. 0 채우기는 y443까지 걸치고, y444부터는 게임
그림이 이미 차 있다. 페이지 15,1 안에 "지워지지도 않고 비어 있는" 21x12는
없다.

## 목표와 제약

회복 수단은 `LoadImage` 후크에서 `owners`를 0xFFFF로 채우는 것이다.
delay slot을 활용해도 9명령 36B가 필요하다.

```
슬롯 28 -> owners 뒤 여유  2B      슬롯 12 -> 34B   (2B 부족)
슬롯 20 ->                18B      슬롯  8 -> 42B   (충족)
```

**8슬롯이 목표다.** 그러려면 캐시 압력이 8 이하여야 하는데 현재 28이다.

## 실측 — 승격 자수와 압력

v232 아카이브 기준, 대사 단위 4,721개 / 동적 글자 434종.

```
승격 자수    최대 압력    8 이하 대사
   39자         18          99%
  150자         11          99%
  182자          8         100%
```

182자면 완전하지만 **목적지 슬롯이 138개뿐**이다(1바이트대 0개,
2바이트대 138개). 138자로 계산하면:

```
138자 승격 후   최대 압력 11
    8슬롯 수용   4719 / 4721 대사   (2개만 초과)
   12슬롯 수용   4721 / 4721 대사
```

**8슬롯에서 밀리는 대사가 2개뿐**이므로 채택한다. 월드맵 이후 전체가
깨지는 현 상태와 비교 대상이 아니다.

## 실행 계획

### v236 — 138자 정적 승격

- 대상: v232 기준 동적 글자 빈도 상위 138자
- 목적지: `free_two` 138개 (509장 비문자 0 + 문자 실적 + 범위표 밖 +
  리맵 밖 + 대본 미참조). v232가 쓴 50칸 이후 남은 전량
- 글리프 원천: **v190 Huffman 산출물**. v231이 v151 폰트에서 색인으로
  뽑아 52/123자가 어긋난 전례가 있다
- 치환: 동적 `E9/EA` 2바이트 토큰 -> 정적 2바이트 코드. 폭이 같아
  포인터와 파일 크기 불변
- v232와의 차이: v232는 정적->정적 이주였고, v236은 동적->정적 승격이다.
  조회표(`n = (lead-0xE9)*254 + arg - 1`) 경유 소스를 셀로 굽는다

### v237 — 8슬롯 축소 + 회복 후크

- `CACHE_N` 28 -> 8, `CACHE_CELLS` 7 -> 2 (상주 안 6개 워드)
- `owners` 16B로 축소, 뒤 42B 확보
- `LoadImage`(0x80177E4C) 진입에 트램폴린, 후크에서 `owners` 전체를
  0xFFFF로 채운다. 히트 판정(`0x801FF49C`)은 **건드리지 않는다**
  (v234가 이걸 nop으로 만들어 중복 10개까지 쌓이며 실패했다)
- 캐시 사각형은 v235의 (999,432) 유지. 8슬롯이면 폭 6칸이라
  x999..1004만 쓰며, 그 범위는 467장 누적에서 완전히 비어 있다

## 정정 (2026-08-16, 실측 후)

위 계획의 핵심 수치 두 개가 틀렸다. 실행 전에 반드시 읽을 것.

### 정정 1 — "138자 승격 시 8슬롯 100%"는 오산

빈도 상위 138자를 그냥 뺀 계산이었고, 그 안에 **1바이트로 직접 참조되는
39자**가 포함돼 있었다. 1바이트 토큰을 2바이트 목적지로 옮기면 폭이 바뀌어
포인터가 밀리므로 실제로는 옮길 수 없다.

승격 대상 138자의 참조 형태 실측:

```
직접 2바이트   65자    승격 가능
E9/EA          33자    승격 가능
혼합            1자    승격 가능
직접 1바이트   39자    불가
```

1바이트 39자를 제외하고 다시 재면:

```
승격 자수      최대 압력    8슬롯 수용
    99자          22         87.3%
   138자          18         88.2%
   395자(전량)    17           -
```

**승격 가능한 전량을 옮겨도 압력은 17에서 멈춘다.** 1바이트 39자가 병목이며
그것이 최고빈도군(다·이·는·지·니·에·을·의…)이다.

### 정정 2 — T4(잔존 일본어 번역)의 슬롯 해방 효과는 0

플랜 T4는 "잔존 일본어를 없애면 1바이트대 가나/한자 슬롯을 해방한다"를
전제했으나 실측 결과 성립하지 않는다.

```
원본과 바이트가 같은 구간(미번역)        164곳
그 구간이 쓰는 1바이트 글자              134종
그중 미번역 구간에서만 쓰이는 슬롯         0개
```

미번역 대사의 1바이트 토큰이 전부 번역된 대사에서도 쓰인다. 원본 일본어
바이트가 가리키던 폰트 칸이 이미 한글로 덮였기 때문이며, 그래서 화면에도
깨끗한 일본어가 아니라 깨진 한글로 나온다(v202 주석의 관찰과 일치).

**번역은 번역대로 가치가 있으나, 캐시 압력이나 슬롯 확보와는 무관하다.**

### 그래서 남은 상태

```
회복 코드 필요량           36B (9명령, delay slot 활용 후)
슬롯 12 -> owners 뒤 여유   34B   (2B 부족)
슬롯  8 -> 여유             42B   (충족)  그러나 압력 17이라 9개가 밀린다
```

**2바이트가 모자라서 막혀 있다.** 확보 가능성이 남은 곳:

1. `next_slot`은 4B로 잡혀 있으나 코드가 `lbu`로 1바이트만 읽는다. 3B를
   회수할 여지가 있다(상주 레이아웃 재생성 필요)
2. 무효값을 `0xFFFF` 대신 1명령으로 만들 수 있는 값으로 바꿔 8명령(32B)에
   맞추는 방법. 단 `0`은 소스 ID 0(니)과 충돌하므로 쓸 수 없다
3. `upload_rect`(8B)를 코드 영역 끝으로 옮기고 그 자리를 쓰는 재배치

### 현재 최선

**v235**다. 캐시 자리 이동이 완성돼 월드맵 지명이 정상 출력되고 owners
중복도 없다. 남은 결함은 월드맵 이후 회복 불가 하나뿐이며, 그것을 고치려면
위 2바이트를 확보해야 한다.

## 회복 수단 — 시도한 경로 전부 (2026-08-16 종결)

v235로 자리 이동은 완성됐다. 남은 결함 "월드맵 이후 회복 불가"를 풀기 위해
아래를 전부 실측했고, 현재 구조에서는 모두 성립하지 않는다.

### 1. 클리어 범위 밖으로 자리 재이동 — 불가

```
y434~442   비행 9칸 · 대화 21칸     0 채우기 구간
y443       경계
y444~467   비행 = 대화             안 지워짐, 그러나 게임 그림이 10~19칸
```

지워지지도 않고 비어 있는 21x12는 페이지 15,1 안에 없다.

### 2. T4 잔존 일본어 번역으로 1바이트 슬롯 해방 — 효과 0

```
원본과 바이트가 같은 구간          164곳
그 구간이 쓰는 1바이트 글자        134종
그중 미번역 구간에서만 쓰이는 것     0종
```

원본 일본어 바이트가 가리키던 폰트 칸이 이미 한글로 덮여, 미번역 구간의
1바이트 토큰이 전부 번역된 대사에서도 쓰인다. **번역은 번역대로 가치가 있으나
슬롯 확보와는 무관하다.**

### 3. 정적 승격으로 캐시 압력 인하 — 부족

```
승격 후보 138자 중 manifest 역매핑 성공   72자 (ui_asset_displaced_static)
                                  실패   66자 (인덱스 56889·51674·16907 …)
```

E9/EA 조회표 값이 물리 인덱스가 아니라 그 66자의 글리프 원천을 특정할 수
없다. v231이 원천을 잘못 잡아 52/123자가 깨진 전례가 있으므로 추측 금지.
승격 가능한 72자로는 압력이 23 근처에 머물러 12슬롯(압력 12 필요)에 못 미친다.

### 4. LoadImage 후크로 owners 무효화 — 공간 없음

무효화 코드는 끝 주소 레지스터를 무효값으로 겸용해 **8명령 32B**까지 줄일 수
있음을 확인했다(decoder에 `0xFFFF` 특별 취급이 없어 임의 무효값 사용 가능).

```
슬롯 28 -> owners 뒤 여유  2B
슬롯 12 ->                34B   (32B 충족)  그러나 압력을 12로 못 내림
슬롯  8 ->                42B                압력 17~23이라 다수가 밀림
```

압력을 못 내리므로 슬롯을 줄일 수 없고, 슬롯을 못 줄이면 공간이 없다.

### 5. 슬롯을 글자 번호 해시로 고정 — 후퇴

같은 글자가 항상 같은 칸을 쓰게 하면 v234의 중복 붕괴가 원리적으로 사라지고
공간도 거의 안 든다. 그러나 충돌이 크다.

```
슬롯수   충돌 없는 대사      밀리는 글자 최대
  28      76.6%              11자
  64      90.1%               4자
```

28슬롯에서 대사의 23%가 손상된다. 현재 순번 배정은 28슬롯에서 100% 수용이므로
명백한 후퇴다. 64슬롯은 48칸이 필요해 자리가 없다.

## 결론과 다음에 볼 곳

**v235가 현재 최선이다.** 결함의 성격이 바뀌었다는 점이 중요하다.

```
v197 (배포본)   월드맵에서 글자·그림 상호 오염, 월드맵 자체도 깨짐
v235            상호 오염 소멸, 월드맵 지명 정상 출력
                남은 결함은 "지나온 뒤 대사 회복 불가" 하나
```

다음에 이어간다면 순서는 이렇다.

1. **E9/EA 조회표 값의 의미 확정.** 66자의 글리프 원천이 풀리면 정적 승격으로
   압력을 12 이하로 내릴 수 있고, 그러면 12슬롯 + 32B 회복 코드가 성립한다.
   이것이 유일하게 남은 정공법이다.
2. 상주 레이아웃 재생성으로 `next_slot` 3B 회수(코드가 `lbu`로 1바이트만 읽음).
   12슬롯에서 37B가 되어 여유가 생긴다.
3. 조합형 폰트는 봉인 유지. 개봉 조건은
   `dynamic_cache_resolution_plan_2026-08-15.md` 참조.
